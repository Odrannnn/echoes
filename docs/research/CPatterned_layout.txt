CPatterned's constructor at 0x80079BE4 - the whole 0xb58 (2904) bytes, split
==========================================================================

Everything below was read out of
build/G2ME01/obj/auto_03_80073CB4_text.o (the retail split of
0x80073CB4..0x8007B0DC), where the constructor sits at section offset 0x5F30 and
`fn_8007A73C` starts at 0x6A88, so 0x6A88 - 0x5F30 = 0xB58 is its exact size. The
body has 726 instructions and 25 distinct call targets.

Nothing here is in the link. `config/G2ME01/splits.txt` gained one NonMatching
range for it (see the report), so the DOL and all 86 RELs still reproduce retail
with retail's own bytes at 0x80079BE4; `ninja` exits 0 and the DOL sha1 is
6ef9b491d0cc08bc81a124fdedb8bfaec34d0010.

The vtable is a separate story: `lbl_803B2458`, 82 slots, 0x148 bytes, mapped in
docs/research/CPatterned_vtable.txt.

2. How the 2904 bytes divide
----------------------------

Every byte of the function is in exactly one row. The region sizes are the
right-hand column of the table in section 1.

  bytes   %    category
  -----  ---   ---------------------------------------------------------------
    292  10.1  the CAi base-constructor call: a 288-byte argument block plus one
               `bl`. No CPatterned logic; it disappears once the aggregate CAi takes
               as its second argument is declared.
   1388  47.8  member initialisation with no call in it: the vtable pointer, x330,
               the two zero vectors, the eleven bit fields (132 B of this), 0x39c
               through 0x448 including all 26 writes to 0x420 (312 B), the CColor,
               x450/x454/x460, x488..x49c, 0x71c..0x7b4, the CActor bit-25 set, the
               clamp of x430_ and the CActor bit-18 clear. This is the part a later
               lane can most cheaply make exact, and 132 B of it already is.
    564  19.4  the three anim-token sequences at 0x66b8, 0x6774 and 0x6830, 188 B
               each. All three are the same boilerplate - a `new (12)`, a gpSimplePool
               virtual call, a CToken copy-ctor or operator=, a local's dtor, the
               pool's dtor and a Lock - differing only in the FourCC ("PART", "ELSC",
               "PART"), the pInfo offset (0xfc, 0x100, 0x110) and the destination
               (0x754, 0x764, 0x780). Every callee is already written or is a
               three-line vtable dispatch, so this is one idiom written three times.
    188   6.5  the x39c_ token rebuild at 0x69b4 - the same boilerplate a fourth
               time, with "SCAN" and a GetObj().
    320  11.0  calls into bodies that are not written, with no logic of its own: the
               two x350_ allocations (104), the CDamageVulnerability
               build/copy/destroy block (72), the model's anim token (36), the six
               sub-object constructors (48), fn_800747A4 (12), the optional CAABox
               pass (48).
    112   3.9  the model-present block at 0x6914: a condition, fn_80079904,
               rstl::string_l("target_LCTR"), fn_8002BE04, one byte store.
    112   3.9  CActor's bit-field group at 0x150: bit 25 set (16 B) and bit 18
               cleared, plus the clamp of x430_ that shares the block.
     24   0.8  the epilogue.

So 47.8% of the function is member initialisation and a further 25.9% is the token
idiom repeated four times; 10% is the base-constructor call; 11% is calls into
unwritten bodies; and only about 4% is a conditional block of CPatterned's own.
Within the member initialisation, 312 B (11% of the whole function) is one
bit-field block whose source shape is not found - section 3 - and 132 B is the
other bit-field block, whose source shape *is* found. Nobody had measured this
split before.


3. The 26-field block at 0x420 - a measured negative result
-----------------------------------------------------------

Retail writes the word at 0x420 twenty-six times, four instructions each
(lwz / rlwimi / stw), with the destination bits 0..25 in order and the shift
always 31-bit. 312 bytes, 11% of the function.

A standalone test compiled with the project's own compiler
(GC/2.7 mwcceppc.exe, the flags from build.ninja) shows that MWCC 2.7 emits
`lbz` / `rlwimi` / `stb` - three instructions, byte granularity - for a run of
one-bit fields in a 4-byte-aligned struct member, and that it does so for `bool`,
`uint` and `short` declarations alike. Assigning all 26 fields `false` in turn
reproduces the *shape* exactly, 78 instructions, but always byte-wise. Retail's
block is word-wise, so no declaration tried reproduces those 312 bytes. The
eleven-field group at 0x34c/0x34d, by contrast, is byte-wise in retail and *is*
reproduced: `bool x34c_24_ : 1;` ... assigned one at a time in a member-init list
gives byte-for-byte the same offsets and shifts (checked against our own
CPatternedCtor.o, which emits 11 rlwimi at exactly 844(r31)/845(r31) with shifts
7,6,5,4,3,2,1,0 and 7,6,5).

The eleven values, read from the source registers: false, (moveType == kMT_Flyer),
false, false, kInvalidUniqueId & 1, false, **true**, false, **true**, false,
**true**. The 26 at 0x420: bits 1, 15, 16 and 17 are set from a register holding 1
and the rest from registers holding 0, so the word ends up 0x00018002. Bit 6 is fed
from a mask (0xF8000000 when moveType == 0) whose bit 0 is always clear, so it is
always false.

6. What promoting this would need, beyond the body
-------------------------------------------------

- The vtable. Neither CPatterned.cpp nor CPatternedCtor.o emits one: MWCC puts it in
  the translation unit that defines the key function, and no CPatterned virtual is
  defined out of line anywhere yet. 82 slots at 0x803B2458, so the unit would also
  have to claim `.data 0x803B2458..0x803B25A0` or every one of those `lis/addi`
  relocations moves.
- The constructor's object carries 32 bytes of `.sdata` and 4 of `.sdata2`
  (CPatternedCtor.o, measured). Per the CAi lesson, an object that contributes
  `.sdata`/`.sdata2` shifts every displacement and every REL import address above
  it, so those two sections have to be worked out before a flip is attempted.
- Six unnamed callees that must exist as symbols for the link: fn_8007A73C,
  fn_800FA748, fn_801BD654, fn_801B7420, fn_801B7E48, fn_801B8C88. They are in the
  binary already under those names, so a `Matching` flip needs no rename for them -
  but the unit must not *define* them.
