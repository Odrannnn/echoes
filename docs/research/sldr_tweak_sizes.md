# The `SLdr*` member layouts, measured out of the Tweaks module

Written 2026-09-26 by lane `e1` at commit `4d49561`, from the Tweaks REL's own
`.text` and nothing else. Every offset and width below is read out of an
instruction; no number is taken from a header, and none is recalled. The method and
the two tools that produce this file are at the bottom.

**This corrects `docs/research/tweak_globals.md`.** That file measured
`sizeof(CTweakContents)` as **0x37D0** against retail's **0x31F4** and attributed the
1,500-byte difference to the generated `SLdr*` headers. The 0x37D0 is an artifact of
the probe: `rstl::string` is `{const char*, control*, uint, rmemory_allocator}`,
which is **16 bytes under `mwcceppc` and 24 on the LP64 host** the probe was compiled
for, and a host probe cannot be made 32-bit here (no multilib). Measured against
retail's own widths, the header's member lists reproduce retail's layout exactly -
see the table below. There is **one** real header defect in the whole set, worth
**+0x50**, in one struct.

## The verdict

| question | answer | where |
| --- | --- | --- |
| retail `sizeof(CTweakContents)` | **0x31F4** (12,788) | `REL_LoadTweaks` does `li r3,0x31F4` before `__nw__`; confirmed by summing the 16 member sizes below |
| does the tree's header list reproduce it? | **yes, 0x31F4, all 16 members at retail's offsets** | table below |
| then what is `tweak_globals.md`'s 0x37D0? | an LP64 artifact: `sizeof(rstl::string)` is 24 there and 16 in the MWCC build | `include/rstl/string.hpp:66-73` |
| is there a real header defect? | **fixed 2026-09-26** (lane `tweaks`): it carried **five members that are not properties of it** (+0x50), now deleted | "The one real defect", below |
| so what is the tree's true `sizeof(CTweakContents)`? | **0x31F4** - retail's, measured (`tools/size_probe_tweaks.cpp`); was 0x3244 | 0x31F4 |

The practical consequence for the boot path is much smaller than
`tweak_globals.md` said, and it is a one-line edit rather than a header-size project.
`REL_CreateTweakGlobals` hard-codes retail's `+0x10E8` for `TweakPlayer`; with the
headers as they stand that member is at `+0x10E8 + 0x50 = +0x1138`, so the fix is to
delete five members from one generated header.

## The one real defect

`include/MetroidPrime/ScriptLoader/SLdrTweakPlayerRes.hpp`, struct
`SLdrTweakPlayerRes_AutoMapperIcons`. The header declares **14** `rstl::string`
members; retail's `LoadTypedef` has **9** properties and retail's constructor ends at
`0x8C`, so retail's struct is **9 x 0x10 = 0x90** and the header's is **0xE0**.

| | retail | header |
| --- | --- | --- |
| properties read by `LoadTypedefSLdrTweakPlayerRes_AutoMapperIcons` | 9 | 14 |
| last member offset | 0x80 | 0xD0 |
| `sizeof` | **0x90** | **0xE0** |

The five that do not belong, with the tags the generator gave them:

| member | tag the header claims |
| --- | --- |
| `mapIconG` | `0x5096bfa5` |
| `mapIconM` | `0xf4e6e0eb` |
| `mapIconR` | `0x65700ccc` |
| `mapIconU` | `0xa0d73242` |
| `mapIconL` | `0x5291eb5f` |

None of those five tags is compared in **any** of the module's 76 `LoadTypedef`
bodies (grepped over `tools/decode_sldr_layouts.py --json`), so they belong to no
struct this lane could find, and the safe change is to delete them: it removes 0x50
and adds no missing member, which is the test the rest of this file passes.

> **Done, 2026-09-26 (lane `tweaks`), and confirmed from the bytes rather than from this file.**
> The five `mapIcon*` members are deleted. The independent evidence that this was the *only*
> defect: `tools/offset_shift_rel.py` re-derived the **+0x50** from retail bytes alone - it is a
> uniform operand delta in six `Tweaks` functions and nothing else in the 385 REL pairs it can
> compare - and after the edit **five of those six went to 100.00%** and the sixth stopped having
> any moved offset at all. `tools/size_probe_tweaks.cpp`, compiled with mwcceppc's own flags and
> read back with `objdump -s`, now gives `sizeof(CTweakContents) == 0x31F4`, `TweakPlayerRes ==
> 0x29B8`, `TweakSlideShow == 0x2EB0`, `TweakTargeting == 0x2F28` - retail's, all four, and
> `SLdrTweakPlayerRes_AutoMapperIcons == 0x90`. **Any figure in this file that says the tree is
> 0x50 over retail is superseded by that**, including the `0x3244` row above and the `residual`
> column's `+0x50` for this struct. The 1,500-byte `0x37D0` in `docs/research/tweak_globals.md`
> was already an LP64 artifact and stays wrong for a second, independent reason.

## What the property tags say, for the structs with a body in the tree

`LoadTypedef<T>` is a counted-property loop: `count = input.ReadUint16()`, then per
property a 4-byte tag and a 2-byte size, then a `switch` on the tag whose `default`
arm is `input.ReadBytes(nullptr, size)`. MWCC compiles the switch to a binary search
over the tags sorted as signed 32-bit, so every tag is a `lis`/`addi` pair feeding a
`cmpw` + `beq`. That is what makes the tag table below readable at all, and it is
also why the tags are *not* FourCCs: they are field-name hashes.

Two things follow that are worth writing down because they are not obvious:

- **The tag in the header comment is not always the tag retail compares.** For
  `SLdrTweakTargeting_LockFire` the header says `0xd4e59e59` and retail compares
  `0xD4E69E59` (`lis r4,0xD4E6; addi r28,r4,0x9E59`). One digit differs in the
  middle. Any body written from the comment would be wrong.
- **A `LoadTypedef` body sees only the properties the struct declares, so a
  constructor is the only source for a member no property writes.**
  `SLdrTweakPlayerControls`'s two nested structs are `UnknownStruct1`/`UnknownStruct2`
  in retail and `Controls`/`Booleans` in the headers; the offsets are unaffected but
  the names are not, and retail's names are what the module's symbols use.

## Three parser facts that cost time, so the next lane does not pay for them

1. **MWCC's objdump separates operands with a bare `,`** - `mr r30,r4`,
   `stw r0,8(r30)` - with no space. Splitting on whitespace silently yields one
   operand and every offset parse returns nothing.
2. **Displacements are printed in decimal, and immediates in decimal too**, while
   objdump prints the *mnemonic* in a form where `mr` and `mr.` are both emitted
   (`mr. r30,r3` in every destructor prologue). Missing the `.` makes `this` look
   like it is never copied out of r3, and every constructor then decodes as empty.
3. **A `rstl::string` contributes three words to a constructor** (buffer, size,
   capacity) and a `CColor` one, so "highest store offset + 4" is not a size. The
   destructor is what separates them: it reaches a string through
   `internal_dereference` and a nested struct through `__dt__<T>Fv`. With that, the
   sizes come out; without it, `SLdrTweakParticle` comes out 0x3C when retail's is
   0x40.
