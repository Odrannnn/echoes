## The two findings worth keeping (both measured, both load-bearing)

**1. A by-value struct argument wants a compound literal, not a named local.** Retail stores each
iterator value into **two** stack words and passes the address of the second: `end` at 0x8 and 0xC
with `r4 = r1+0xC`, `begin` at 0x10 and 0x14 with `r3 = r1+0x14`. It also loads `mItems` **twice**
(0x801E5494 for `end()`'s `data() + mCount`, 0x801E54B0 for `begin()`) — 13 of `fn_801E5458`'s 46
instructions.

| spelling of the two arguments | result |
| --- | --- |
| two named `Iter` locals assigned before the call | **45 instructions**, one `lwz r0,12(r29)` (CSE'd), arg slots at 0x8/0xC |
| two **compound literals** `(Iter){...}` as the arguments | **46 instructions**, slots 0x8/0xC/0x10/0x14, **byte-exact** |

So `(SPortalIter801E5458){self->xc_items}` is not decoration. Cost of getting it wrong: 1 of 46
instructions and 2 wrong argument offsets, which would have failed the flip with a 99.99% looking
object.

**2. Leaving `end` in the parameter is what fixes `fn_801E5510`'s registers.** Retail has
`lwz r6,0(r3)` (cursor in `r6`), `lwz r0,0(r4)` (end in `r0`) and `r3` as the per-word scratch.
Hoisting `end.current` into a named local — the spelling anyone reaches for — is still 19
instructions but gives `r3`/`r4` for the cursors and `r0` as the scratch, i.e. 12 wrong words.
The shipped body reads `end.current` from the parameter inside the loop test and copies out only
`begin`. Same family as the `IsAllocValid` finding ("the register a temporary lands in is a
function of how the expression is written").

## Things a next run should not re-derive

* **Plain `.c` worked** — no need for `Carve80233A90.cpp`'s `.cpp` + `extern "C"` escape. The `fn_`
  names stay unmangled and the object emits exactly `fn_801E5458` / `fn_801E5510`.
* **The empty `for` in `fn_801E5458` is real and must stay.** It is `rstl::destroy(mItems,
  mItems + mCount)`: `is_trivially_destructible<SPortalState>::value` is **false** (primary
  template, `include/rstl/construct.hpp:26-29`), so `destroy_impl`'s loop survives
  (`construct.hpp:101-109`) while `SPortalState`'s own destructor is trivial and emits nothing.
  `include/rstl/construct.hpp:31-42` already documents this mechanism. Deleting the loop removes 3
  of 46 instructions and is a regression, not a cleanup. The `cmplwi r5,0 / beq` guard in the copy
  is `construct_impl`'s placement new (`construct.hpp:53-56`).
* **Only 2 undefined symbols**: `allocate__Q24rstl17rmemory_allocatorFi` (0x802FDAB8,
  `symbols.txt:13824`) and `Free__7CMemoryFPCv` (0x802CE388, `symbols.txt:12992`). Both are
  retail's own, so **no `PortLinkStubs.cpp` entry** was needed and none exists to delete.
* The claim starts at `fn_801E5458`, not where a `Matching` unit ends — the nearest claimed range

  link-order cycle `RUNNING_THE_DECOMP.md` records for that case does not apply.
* `auto_03_801E52D0_text` now runs 0x801E52D0..0x801E5458 and 0x801E555C..0x801E7038 as two
  objects; 0x188 + 0x104 + 0x1ADC is the 0x1D68 it was.
* `tools/unit_fit.sh` reports 8 bytes of `.sbss2` (`@17`, `@19` — MWCC's unnamed statics for the two

* `tools/check_decl_order.py --unit <name>` prints "0 unit(s) checked" for a `Matching` unit — by

## How to iterate on a carve body quickly

`tools/probe_cc.sh <src> <out.o>` (documented in `RUNNING_THE_DECOMP.md`'s tools table) compiles
one scratch source with the exact DOL flags. Compile the candidate, `objcopy -O binary
--only-section=.text`, and diff the byte stream against `python3 tools/dol_read.py <start> <size>
orig/G2ME01/sys/main.dol` — do **not** diff against `build/G2ME01/main.elf` once the unit is in
the link, or you are comparing the unit with itself.
