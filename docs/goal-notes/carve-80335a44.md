## The body, and the one thing that is easy to get wrong

```
fn_80335A44    lwz r0, 0x44(r3) / li r3, 0 / rlwinm. r0, r0, 0, 23, 23 / beqlr / li r3, 2 / blr
```

```c
int fn_80335A44(void* self) {
  unsigned int w = *(unsigned int*)((unsigned char*)self + 0x44);
  int r = 0;
  if (w & 0x100u) { r = 2; }
  return r;
}
```

**The bit is 8, not 23, and the parent item's note is wrong about it.**
`docs/goal-notes/carve-80218c64.md` reads the mask as "bit 23", which is the LSB numbering;
`rlwinm`'s MB/ME count **from the MSB** (MB = 0 is the sign bit), so `MB = ME = 23` keeps bit
31-23 = 8, i.e. `0x100`. Measured, compiling ten single-bit masks through MWCC 2.7 at the
project's flags and reading the emitted rotate back:

| source mask | emitted | | source mask | emitted |
| --- | --- | --- | --- | --- |
| `& 1u` | `rlwinm r3,r3,0,31,31` | | `& 0x8000u` | `rlwinm r3,r3,0,16,16` |
| `& 2u` | `rlwinm r3,r3,0,30,30` | | `& 0x10000u` | `rlwinm r3,r3,0,15,15` |
| `& 8u` | `rlwinm r3,r3,0,28,28` | | `& 0x800000u` | `rlwinm r3,r3,0,8,8` |
| `& 0x100u` | **`rlwinm r3,r3,0,23,23`** | | `& 0x4000000u` | `rlwinm r3,r3,0,5,5` |

`0x800000` (what a first reading of the asm suggests) gives mask 8, and `0x100` gives retail's
23. The repo's own Matching units agree independently: `CActor.cpp`'s `sfxId & 0x20000` (bit 17)
is `rlwinm. r0, r4, 0, 14, 14` at `build/G2ME01/asm/MetroidPrime/CActor.s:1081`, and 31-17 = 14.
**This costs an hour if you do not know it, so it is the first thing to try on the other 32
functions `carve-80218c64` lists.**

**The `int r` is load-bearing too.** MWCC if-converts a two-armed select of constants into
arithmetic, and `beqlr` is what stops it:

| spelling | emitted `.text` |
| --- | --- |
| `? 2 : 0` | `lwz r3,68(r3) / li r0,2 / rlwinm r3,r3,9,31,31 / neg r3,r3 / and r3,r0,r3 / blr` |
| `if (c) { return 2; } return 0;` | same branchless form |
| `if (c) { return 2; } else { return 0; }` | same branchless form |
| `int r; if (c) { r = 2; } else { r = 0; } return r;` | same branchless form |
| `switch (c) { case 0x100u: return 2; default: return 0; }` | `lwz / rlwinm / cmpwi / beq / b / li / blr / li / blr`, 0x24 = 36 bytes |
| **`int r = 0; if (c) { r = 2; } return r;`** | **retail's 24 bytes** |

All measured at `-O4,p` on this tree's flags; the last row also matches if the `w` local is
dropped (`int r = 0; if (*(unsigned int*)(...) & 0x100u) { r = 2; } return r;`) or if `r` is
`unsigned`. No spelling was searched before this one - the mask was the whole problem.

`.c`, not `.cpp`, because `symbols.txt:15077` gives it the placeholder `fn_80335A44` and only an
unmangled C definition reproduces it, as with the neighbouring carves of this run. The definition
order question does not arise with one function; `check_decl_order.py --unit` reports
`0 unit(s) checked` on a carve, as it did on `Carve80218C30.c`, so `flip_test.sh` and the DOL
sha1 are the real checks and both passed.

## Notes for the next run

- **`rlwinm`'s MB/ME are numbered from the MSB** (see the table above). Any DOL or REL function
  whose asm reads `rlwinm …, N, N` as a bit test wants mask `1 << (31 - N)` in the source, and
  getting it backwards costs a search: `fn_80335A44` was the whole item and the first four
  spellings tried all emitted mask 8. `find build/G2ME01/asm -name '*.s' | xargs grep -lE
  'rlwinm\.? +r[0-9]+, r[0-9]+, 0, 23'` matches 22 files, every one of which is a bit test
  written the LSB way and has to be re-read the MSB way before its source can be written.
- **MWCC if-converts `cond ? 2 : 0` and `if (c) return 2; return 0;` to arithmetic**, 5
  instructions with no `beqlr`. Assigning through a `0`-initialised local is what keeps the
  branch. Relevant to any `li r3, 0` / `beqlr` / `li r3, N` shape in the unsourced `auto_*` units,
  which is most of them.
- **The parent item's other 32 functions are the cheap queue and the list is still good**, but two
  of its claims need re-measuring rather than trusting: the `force_active:` one (false here, above)
  and the bit-23 one (false here, above). `fn_80335A5C`-style `li r3,0` stubs need neither fix and
  are the cheapest ones on the list - `fn_80335AA4` (0xC), `fn_8033719C` (0x8), `fn_803371F4`,
  `fn_80335B30` (0x8) and the rest of the run are all 8-byte bodies beside already-matched code.
- **The neighbourhood is one address run, and the remaining gaps in it are worth one item each**:
  `auto_03_80335A0C_text` holds `fn_80335A0C` (0x8, `lfs f1, lbl_8041ECE8@sda21(r0)`) and
  `auto_03_80335AA4_text` holds `fn_80335AA4` (0xC, `stw r4,0x1c(r3) / stfs f1,0x4(r3)`) - both
  exact single-function gaps between carved neighbours, so each is a `.c` carve with no
  `force_active:` question to answer (they do carry `@sda21`/float sections, which is what makes
  them slightly more than a `li r3,0`).
- **`unit_fit.sh` needs the extension it really has** - it appends `.cpp` to a bare name and then
