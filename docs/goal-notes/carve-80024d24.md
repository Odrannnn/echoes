## How the two functions were identified

The element is **`CFontImageDef`**, and the measurement that fixes it is the caller: the unclaimed
`fn_80024CD4` (0x80024CD4, 0x50) is an element walk whose stride is `addi r31,r31,0x1c`, and
`include/Kyoto/Text/CFontImageDef.hpp:41` is `CHECK_SIZEOF(CFontImageDef, 0x1c)`. So
`fn_80024D44` = `destroy_impl` (`li r4,-1 ; bl __dt__13CFontImageDefFv`, the -1 being MWCC's
"do not free me" flag - the callee's own `extsh. r0,r31` at 0x80024D94 proves 16-bit) and
`fn_80024D24` = the `destroy` forwarder over it (`include/rstl/construct.hpp:84-90` / `:92-95`).

Three already-matched copies of the same nine/ eight instructions exist in this tree, and I
verified each from `orig/G2ME01/sys/main.dol` with `tools/dol_read.py` before writing them into the
header: `fn_80004C6C`/`fn_80004C4C` (`src/MetroidPrime/Player/Carve80004C4C.c`, the seeder's twins
for these two), `destroy_impl< 11CTweakValue >__4rstlFP11CTweakValue` (0x80006850, 0x24) and
`fn_80004D3C` (0x80004D3C, 0x20, the seeder's twin for `fn_80024D24`) / `__sys_free` (0x80008A28,
0x20). `fn_80024D44` reproduces retail's own instruction order (`li r4,-1` between `mflr r0` and
`stw r0,0x14(r1)`), which the twin has too.

**Read retail's bytes from `orig/G2ME01/sys/main.dol` via `tools/dol_read.py`, never from
`build/G2ME01/main.elf`** - that ELF is our own build. (Same lesson as `carve-80024b70`.)
