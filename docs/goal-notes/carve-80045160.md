## The body, and why the spelling was not a guess

The seed pointed at retail's address twin `fn_80044F1C` (0x80044F1C, 0x6C). There is a better
twin, already `Matching` in this tree, that fixes the spelling outright:

**`fn_80281310` in `src/MetroidPrime/Carve80281310.c`** — 0x80281310, 0x6C = 108 bytes,
**27 instructions**, 100% in `build/report.json`. It is the same loop for a 0x10-byte element, and
it is instruction-for-instruction the same shape: the same 0x20 frame, the same
`mr r31,r3` / `li r30,0` / `mr r29,r5` / `mr r28,r4` cursor setup **in that order**, the same
`b` to the bottom test, the same `mr r3,r31` / `mr r4,r29` / `bl` call, the same
`addi r30,r30,1` then `addi r31,r31,<stride>` pair, the same `cmpw r30,r28` / `blt`, and no
`mr r3,...` before the epilogue. Two words differ: the stride (`0x10` there, `0x2C` here) and
the `bl`. So `char* cur`, the hoisted `int i`, and
`for (i = 0; i < count; ++i, cur += 0x2C)` are the twin's, copied.

What it is: `rstl::uninitialized_fill_n` for the 0x2C-byte element — n elements each built from
the *same* source, which is why `r5` is never advanced. The 0x2C stride is retail's statement of
the element size (44 bytes), the same element `Carve80045014.c`'s `fn_80045014` copies.

**Parameter order** is fixed by the only caller, `fn_80045128` at 0x80045128 (0x38,
`auto_03_8004509C_text.s:52-68`): `stw r4,0x0(r3)` / `addi r3,r31,0x4` / `bl fn_80045160` /
`mr r3,r31`. So `r3` = destination array, `r4` = count, `r5` = value.

**No `PortLinkStubs.cpp` entry was needed**, and that is measured rather than assumed: the one
`bl` target, `fn_8004507C` (0x8004507C, 0x20), is 0x68 bytes *below* this claim and is already
defined by `MetroidPrime/Carve80045014.c` (`Matching`, 0x80045014..0x8004509C), so the reference
resolves to a real definition in the DOL link. The unit declares it and never defines it.
`fn_8004509C`, the one step further down, is not called from this claim at all.

## A recorded negative result: the documented link-order cycle did **not** happen

`docs/RUNNING_THE_DECOMP.md:2049-2055` says carving a range out of an `auto_*` run "which starts
exactly where [a] `CFrustumPlanes.cpp`'s `.text` ends" fails `dtk dol split` with
`Cyclic dependency ... CFrustumPlanes.cpp -> auto_03_803029D8_text` **before anything compiles**,
and that "proximity to an existing unit boundary is not [fine]".

This carve is exactly that shape: `auto_03_8004509C_text` starts at 0x8004509C, which is where
`MetroidPrime/Carve80045014.c`'s `.text` ends. `dtk dol split` accepted it, the build linked, and
the DOL sha1 held. So the cycle is a property of the particular call graph, not of boundary
proximity — worth knowing before deciding a carve is impossible on that ground. (dtk also split
the run around the claim, as documented: `auto_03_8004509C_text` is now 196 bytes / 3 functions
(`fn_8004509C`, `fn_800450C4`, `fn_80045128`) and the tail became `auto_03_800451CC_text`, 12
functions.)
