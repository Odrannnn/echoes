## Three findings the item did not carry, all measured

**1. The callee is retail's `list<T>::do_insert_before`, and this tree already matches it 0x338
bytes away.** `fn_801E36AC` (0x801E36AC, `symbols.txt:7800`, 0xA0 = 160 bytes, 40 instructions)
is the **same forty instructions in the same order** as `fn_801E3374` (0x801E3374,
`src/MetroidPrime/ScriptObjects/Carve801E3334.cpp:105`, `Matching`, 100.00%), which that
neighbouring unit has already matched as `do_insert_before` for
`rstl::list<rstl::pair<TUniqueId, float>, rstl::rmemory_allocator>`. The two differ only in the
value copy —

| | key at +0 | second member at +4 |
| --- | --- | --- |
| `fn_801E3374` (`pair<TUniqueId,float>`) | `lhz r0,0(r30)` / `sth r0,0(r4)` | `lfs f0,4(r30)` / `stfs f0,4(r5)` |
| `fn_801E36AC` | `lhz r4,0(r30)` / `sth r4,0(r5)` | `lwz r0,0x4(r30)` / `stw r0,0x4(r5)` |

— and in the one `bl` target. That fixes the callee's argument order, the 0x10-byte node
(`li r3,0x10` + the `addic. r5,r3,8` placement offset), `mCount` at +0x14 as the last thing it
touches, and **that the element is `rstl::pair<TUniqueId, int>`** — a halfword key and a whole
word, not a float. `fn_801E3684` never touches the element, only forwards its address, so none of
that had to be spelled to match; it is in the header as provenance.

**2. The value arrives as a pointer, and the one caller proves the receiver is the list at +0x44.**
`grep -rn 'bl fn_801E3684' build/G2ME01/asm/` returns exactly one call site, 0x801E34F4 inside

(`sth r5,0x20(r1)` / `sth r5,0x70(r1)` / `stw r0,0x74(r1)` with `r0 = 0`). That is the same
halfword-plus-word the callee copies, so `const void*` for `val` is what the bytes say, not a
convenience. `Carve801E3864.c` supplies the other half from the opposite side: its header
