The item asked for `0x80024B70..0x80024CD4` (3 functions, 0x164 bytes). **I claimed the contiguous

## What `fn_80024B70` is, and how it was read off

`rstl::vector<TToken<CCharLayoutInfo>>::~vector()` in MWCC's deleting-destructor form, 42
instructions:

- `lwz r0,4(self)` = `mCount`, `lwz r30,0xc(self)` = `mItems` (`include/rstl/vector.hpp:18-21` is
  `mAllocator`, `mCount`, `mCapacity`, `mItems`).
- `slwi r0,r0,3` is `mItems + mCount` at `sizeof(T) == 8`; `TToken<T>` adds nothing to `CToken`,
  which is `CObjectReference* mObjRef` + `bool mLockHeld` (`include/Kyoto/CToken.hpp:33-36`).
- the loop's `cmplwi r30,0` / `beq` before `bl __dt__6CTokenFv` (`li r4,0`) is `destroy_impl`'s
  null test.
- the first `bl Free__7CMemoryFPCv` is `deallocate(mItems)`; the second is the flag-guarded release.
- **the four stores at `r1+0x14/0x10/0x0C/0x08` are the inliner's two by-value
  `pointer_iterator` home slots, not dead writes** — deleting them is 16 bytes short and does not
  match (measured). Same four documented at `src/MetroidPrime/Carve800045A0.c:26-30`.

Both callees are declared, never defined here: `Free__7CMemoryFPCv` (0x802CE388) is claimed by
`Kyoto/Alloc/CMemory.cpp` and `__dt__6CTokenFv` (0x8030154C) by `Kyoto/CToken.cpp`, so the three
`bl`s resolve inside our own tree. `check_symbol_names.py` is clean and no `PortLinkStubs.cpp`
duplicate exists (grepped: no `fn_80024B70` there).

## The port link: one required addition to `src/Kyoto/Alloc/PortMwccNew.cpp`

The carve's `bl __dt__6CTokenFv` is a real reference, and on a **host** link that retail-mangled
name binds to nothing, so `tools/link_check.sh` went 291 -> **292 undefined** and `gate.sh`'s
`port probe` step failed the item even though the DOL was byte-exact. Fixed the way this repo
already fixes that class of problem, next to the existing `Free__7CMemoryFPCv` definition
(`src/Kyoto/Alloc/PortMwccNew.cpp:34`): added

```c
extern "C" void __dt__6CTokenFv(void* self, short) {
  static_cast< CToken* >(self)->~CToken();
}
```

plus `#include "Kyoto/CToken.hpp"`. The 16-bit second argument is MWCC's deleting-destructor flag;
the only call site passes 0, so it is accepted and ignored and the work is `CToken`'s own
destructor. After this, `link_check.sh` reads **291 undefined, unchanged from baseline** and the
gate's probe step is green.

## WALL: fn_80024C18 3/33 - only stack-slot assignment, ~45 spellings tried

`fn_80024C18` (0x80024C18, 0x84 = 132 bytes) is
`rstl::vector<CWorldSaveGameInfo::SEnvironmentVariable>::~vector()` - `mulli r0,r0,0x1c` fixes
`sizeof(SEnvironmentVariable) == 0x1C` (`include/MetroidPrime/CWorldSaveGameInfo.hpp:62`) - and it
is **3 instructions from retail**, all of them frame-slot displacements:

```
+11   retail 3881000c  addi r4,r1,0xc     ours  addi r4,r1,0x10
+14   retail 90a1000c  stw   r5,0xc(r1)   ours  stw   r5,0x10(r1)
+17   retail 90010010  stw   r0,0x10(r1)  ours  stw   r0,0xc(r1)
```

Retail's frame is `0x08=end 0x0C=end 0x10=begin 0x14=begin`, each value's two by-value copies in a
**contiguous pair**, and it hands `fn_80024C9C` `r3 = r1+0x14` (begin) and `r4 = r1+0x0C` (end). The
best I reached is `0x08=end 0x0C=begin 0x10=end 0x14=begin` - same four words, grouped by role
instead of per argument. The code is semantically identical and both argument registers already
carry the right values, so this is pure stack-slot allocation.

What got there, and what did not (each measured, non-`bl` differences):

| spelling | diffs | note |
| --- | --- | --- |
| named `begin`/`end` locals, `fn_80024C9C(&begin,&end)` | 19 | **124 B / 31 insns - 2 instructions short**, retail has 4 home-slot stores, this has 2 |
| by-value params on `fn_80024C9C`, named locals | 20 | **128 B / 32** - 1 short |
| `volatile` locals x4 (two copies each) | 21-25 | 136-144 B, too long |
| `struct SEnvVar* volatile last` temporary | 24-25 | too long; the accumulator leaves `r5` |
| `MakeIt(p)` non-inline helper | 8 | right length **but emits an extra `MakeIt` symbol retail does not define** |
| `static inline` MakeIt + `#pragma inline_max_size(1000)`, args as call results | **3** | right length, no extra symbol - the plateau |
| same, argument order reversed (`eb`) | 9 | |
| `MakeBegin(self)` / `MakeEnd(self)` split helpers, both orders | 3 / 9 | same plateau |
| `MakeIt(self, p)` taking self as well | 3 / 9 | same plateau |
| comma operator forcing `end`-first evaluation | 3 | same plateau |
| out-parameter helper (`FillIt(&b,...)`) | 20 | 128 B, 1 short |
| `const` locals | 18 | 128 B, 1 short |
| `&self->mItems[count]` index form | 20 | |
| separate named temporaries per copy | 18-26 | |
| callee declared `(end, begin)` instead of `(begin, end)` | 3 | no change to the layout |

**The two findings worth keeping.** (1) **MWCC will not fold two reads of the same field**: retail's
`fn_80024C18` loads `self->mItems` twice (`lwz r5,0xc(r30)` at 0x80024c40 and `lwz r0,0xc(r30)` at
0x80024c54) because `~vector()`'s source is `destroy(begin(), end())` - two calls, each reading
`mItems` itself. In C a named local gives one load, and that is the whole 8-byte deficit. Getting
the second load needs the arguments to be **call results**, i.e. an inline helper - and the helper
must be `static inline` or it is outlined and `unit_fit.sh` fails on a symbol retail does not have.
(2) Once the helper is in, the length is right and only the slot grouping is wrong, and that does
not move across ~20 further variants. Note the accumulator must also land in `r5` (retail's
`add r5,r5,r0`), which is what any `volatile` temporary breaks.

`fn_80024C9C` (0x80024C9C, 0x38 = 56 bytes) **was** reached byte-exact in the same experiment: the
outlined `rstl::destroy`, taking its two iterators **by value**, reading `*(r4)` before `*(r3)` and
forwarding `&begin, &end` to `fn_80024CD4`. Its body is in the notes above because it is the
callee whose argument-passing convention `fn_80024C18` has to match.
