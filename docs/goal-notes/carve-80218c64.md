## The dead strip, and why `config.yml` is in this diff

**This is the thing to read.** The unit compiles byte-for-byte correct and the DOL still breaks.

First build, with only the four carve files:

```
build/G2ME01/main.dol: FAILED
... 86 RELs: FAILED ... WARNING: 87 computed checksum(s) did NOT match
```

`sha1sum build/G2ME01/main.dol` -> `4e19491bb41cc8af57e055e7654a1ba11c11978c`, **3,968,992 bytes
against retail's 3,969,024**, and the DOL header showed `.bss` at `0x803a5470` against retail's
`0x803a54a0`. `python3 tools/dol_read.py 0x80218C64 0x34 build/G2ME01/main.dol` printed

```
hex : 90 6d 96 b8 4e 80 00 20 94 21 ff f0 7c 08 02 a6 90 01 00 14
      80 cd 96 c0 81 86 00 04 7d 89 03 a6 4e 80 04 21 ...
```

i.e. `fn_80218C64` is right and at 0x80218C6C there is **`LoadSplitterCommandModule`'s** body
(`80 cd 96 c0 / 81 86 00 04 / mtctr / bctrl`): mwldeppc dropped `fn_80218C6C` and slid the next
object up by exactly its 0x2C bytes, so every later address in the image moved and the `.data`/`.bss`
that follow it moved with them.

`build/G2ME01/ldscript.lcf`'s FORCEACTIVE block has 1901 entries and contains `fn_80218C30`,
`fn_80218C64`, `fn_80218CF0` and `fn_80218B68` - the other four script-loader setters already carved

below), and while it lived in a dtk auto unit that was harmless: dtk's auto units are raw bytes and
are not dead-stripped. Making it a real object is exactly what exposes the gap.

The fix is the documented one for this trap - `config/G2ME01/config.yml`'s `force_active:`, which
`docs/RUNNING_THE_DECOMP.md` records for REL modules (`ForgottenObject`, `AtomicAlpha`). **It also
works as a top-level key for the main module**, which the docs do not say and which is new here:

```yaml
force_active:
  - fn_80218C6C
```

After it: `87 files OK`, `main.dol` back to `6ef9b491d0cc08bc81a124fdedb8bfaec34d0010` and
3,969,024 bytes, all 86 REL hashes unchanged. So **a carve of a DOL function that retail's own
FORCEACTIVE list does not name needs a top-level `force_active:` entry, or the function is silently
stripped and the whole DOL shifts.**

## The record, and why `fn_80218C6C` reads `+0x8`

The record is `lbl_75_bss_20`, `.bss:0x20`, **`size:0x18`** in
`config/G2ME01/rels/Splitter/symbols.txt`, filled by `fn_75_8254`
(`src/MetroidPrime/ScriptObjects/CSplitterRelMain.cpp:84-88`) with three members: two 4-byte loaders
from the module's own `.text` and a 12-byte CodeWarrior pmf copied out of `.data` - 0x14 bytes of
content in retail's 8-byte-aligned 0x18 object. So the pmf is at **+8**, which is the
`addi r12, r4, 0x8`. The two loaders are the ones the `Matching`
`src/MetroidPrime/ScriptLoader/SplitterMainChassis.cpp` already dispatches: its asm is
`lwz r12, 0x0(r6)` for `LoadSplitterMainChassis` 0x80218CC4 and `lwz r12, 0x4(r6)` for
`LoadSplitterCommandModule` 0x80218C98.

Two things this corrects or pins down:

* **`CSplitterRelMain.cpp`'s "nothing in the DOL reads it" (about the third member) is wrong** -
  `fn_80218C6C` reads words 2, 3 and 4 of that record through `__ptmf_scall`, which is `this_delta`
  at +8, `vtbl_offset` at +12 and `func_data` at +16. It missed it because it grepped the *claimed*
  units; this function was in a dtk auto unit. I did not edit that file - it is a `Matching` unit's
  comment and out of scope for this item - but the next reader should know.
* **the pmf's argument list is `(float)`, measured on the module side**: `fn_75_5A54` (0x5A54, 0x2C
  bytes) stores the incoming `f1` at `+0xef0`, and `CSplitterRelMain.cpp` already spells the member
  `void (CEntity::*method)(float)`. **`fn_80218C6C` itself shows no float instruction at all**, so
  these 44 bytes cannot say how many arguments its caller passes; the body takes the one the record
  is measured to have, and `__ptmf_scall` (`src/Runtime/ptmf.c:31`) reads only r12 and r3 and
  leaves `f1` alone, so the argument reaches the callee untouched either way. **A different spelling
  with no `float` parameter would emit the identical 44 bytes** - so this choice agrees with the
  `Matching` unit that measured it rather than being derived from these bytes.

`r4` rather than `r5` for the loaded slot is what says the signature has no second integer argument:
every loader thunk in this family takes three (`mgr`, `input`, `info` in r3/r4/r5) and every one of
them loads into **r6** - `LoadSplinter` 0x80218C38, `LoadSplitterCommandModule` 0x80218C98,
`LoadPlayerActor` 0x8021BC6C all do `lwz r6, gLoader_...; lwz r12, 0x0(r6); mtctr r12; bctrl`.
`TouchPlayerActor` uses r5 because r4 is its live `mgr`. So r4 being free means r3 is the only
integer parameter, i.e. the receiver.

## Nothing calls `fn_80218C6C`, and that is measured

* Every `bl` in `.text` (`build/G2ME01/main.dol`, file offsets 0x640..0x3A22A0, target = site +
  sign-extended I-form displacement, `vaddr = fileoff + 0x80003200`): **no** branch to 0x80218C6C and
  **no** branch to 0x80218C64. The same scan finds all 28 `bl __ptmf_scall` sites and
  `bl 0x8021BA94` at 0x8003CB18, so the scan works.
* The literal 4-byte big-endian value `0x80218C6C` anywhere in the 3,969,024-byte image: no hits, so
  no data reference either.
* No REL imports it: `config/G2ME01/symbols.txt:9495` is the only mention in the whole config tree,
  and module 75's own imports are `fn_80218CF0`, not this.

So retail left it unreferenced. Nothing needs a dead-strip-proof entry beyond the one above, and
nothing in the port has to call it - which is why this is a carve of bytes and not a fix.
`fn_80218C64` *is* called, by module 74 (`CSplinterRel.cpp:73-74`): `RELExit` at `.text:0xA4`
(0x24 bytes) does `li r3, 0x0 / bl fn_80218C64`, and `fn_74_E8` at `.text:0xE8` (0x30 bytes, reached
from `RELMain` at 0x0C8) does `stwu r0, lbl_74_bss_70@l(r3)` and then `bl fn_80218C64` with r3 still
on the record - which is why the parameter is a pointer to one and not a loader.
