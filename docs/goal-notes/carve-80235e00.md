### Why `.c` and why unmangled

```
$ strings build/G2ME01/DarkCommando/DarkCommando.plf | grep 80235E00
fn_80235E00
```

The module imports the plain retail name, so the definition must be that exact symbol; a `.cpp`
would mangle it and the two `bl fn_80235E00` would resolve to nothing.
`src/MetroidPrime/ScriptObjects/CDarkCommandoRel.cpp:165` declares it `extern "C"` and only
declares it — no other unit in `src/` defines it, so there is exactly one definition. The
carve's `splits.txt` entry therefore removes it from `main/auto_03_80235E00_text`, which still
exists for the remaining 0x80235E08..0x802392A4 (0x34A4 - 8 = 0x349C bytes).

### The slot stays where it belongs

`gLoader_DarkCommando` is claimed and defined by
`src/MetroidPrime/ScriptLoader/DarkCommando.cpp` (`splits.txt:2058-2060`, `.sbss 0x80419660..68`),
whose `.text` ends exactly at 0x80235E00. This unit claims `.text` only and takes the slot as
`extern`, which is what keeps it defined in exactly one unit. MWCC does not encode a variable's
type in its name, so the declaration resolves to `gLoader_DarkCommando` itself.

`DarkCommando.cpp:6-8` says the setter "is deliberately NOT claimed: REL modules import it by
its retail name, so it cannot be renamed and must stay in dtk's auto unit". **That sentence is
now superseded by this file** — the import is the plain `fn_80235E00`, so defining it unmangled
here keeps the symbol in the DOL link and both module call sites still resolve, with nothing
renamed. This is the same supersession `PuddleSpore.cpp` went through in
`docs/goal-notes/carve-8022a058.md`; I did not edit that file (the driver discards doc edits
outside the notes file) and have recorded the correction here instead.
