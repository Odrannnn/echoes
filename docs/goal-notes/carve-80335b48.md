## Notes a next run can use

- **Both functions are virtual**, which the item does not say and which is the only
  interesting fact about them. `build/G2ME01/asm/auto_07_803BBB68_data.s` lines 31-32 list
  `fn_80335B48`, `fn_80335B50` as consecutive vtable entries of `lbl_803BBB68`
  (`symbols.txt:18732`, `size:0x1F0`), and `auto_07_803BB288_data.s` repeats the same
  adjacent pair at lines 213-214, 406-407 and 493-494 - four vtables in total. So they are
  reached through vtable slots and no caller exists to read a signature off; the two
  instructions are the whole of the evidence for what they do.
- **The struct is declared by offset, deliberately.** Retail names no class for these slots,
  and no class in `include/` has a float at +0x4 *and* an int at +0x1C, so the two words
  live in a local `SCarve80335B48` whose only claims are the offsets the instructions name -
  the same treatment `src/MetroidPrime/Tweaks/Carve80216D2C.c` gives `CTweakGame`. Nothing
  between +0x8 and +0x1B is asserted and nothing reads it. A future run that identifies the
  owning class can replace the local struct with the real header without touching the
  bodies.
- **No `TARGET_PC` arm is needed and none was written.** `grep` finds neither symbol outside
  `config/G2ME01/symbols.txt`, and the only tables that reference them are the unclaimed
  `auto_07_*` `.data` objects that retail's DOL supplies and the host link does not carry.
  The bodies below are therefore the DOL's, offsets and all, exactly as compiled.
- **Adjacency here is benign, and worth stating because the carve vein has a cycle trap.**
  The claim starts at 0x80335B48, which is exactly where `Kyoto/Math/Carve80335B38.c`
  ends, and ends where `Kyoto/Math/Carve80335B58.c` starts. That is the same adjacency
  `FACTS.md`'s third carve trap warns about (a range beginning on a unit boundary can fail
  `dtk dol split` with `Cyclic dependency ... link order`), and it did not: the entries are
  in address order in all three files and the build links. The trap is about ordering, not
  adjacency as such.
- **The twin's C is not the twin's class.** `fn_80335B48` and `fn_80335B50` share bytes with
  a `CSfxManager::CBaseSfxWrapper` setter and a `CGameOptions` setter respectively, but
  those two are different classes with different layouts; the pair being vtable-adjacent is
  what puts them in one carve. Writing either body against its twin's real class would have
  produced the right instructions here by accident and the wrong offsets everywhere else.
