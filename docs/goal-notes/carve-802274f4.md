## The one thing that cost time: ascending source order, and how it showed up

Written ascending on the first attempt (`fn_802274F4` before `fn_802274FC`) — 0x802274F4 is the
**lower** address, so descending means `fn_802274FC` first. mwccppc reversed it as documented, so the
object came out `fn_802274FC` at offset 0 and `fn_802274F4` at offset 8, mwldeppc placed the object
verbatim at 0x802274F4, and **both module call sites bound to the wrong function**.

The signature is worth recording because it is not the one the docs describe. `ninja` reported
`main.dol: FAILED`, `GeomBlobV2.rel: FAILED`, `Krocuss.rel: FAILED`, `84 files OK` — i.e. the
**two RELs that import these functions are the diagnostic**, and 84 other RELs were untouched. The
two `bl` words in `Krocuss.rel` at file offsets 0x3030 and 0x3038 read `802274f4` in
`orig/G2ME01/files/RelProd/Krocuss.rel` and `802274fc` in ours. `unit_fit.sh` said "fits", objdiff
would have said 100%, and the link succeeded: only `flip_test.sh` / the sha1s caught it, which is
the rule working. Swap the two definitions and all 87 hashes hold.
