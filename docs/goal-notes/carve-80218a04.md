## What the carve is

`.text 0x80218A04..0x80218A0C`, `0x8` = 8 bytes, **1 function**, the whole of dtk's
`auto_03_80218A04_text` (`config/G2ME01/symbols.txt:9472`):

```
fn_80218A04  0x80218A04  0x8   stw r3, gLoader_FlyingPirate@sda21(r0)
                              blr
```

It is the DOL side of the FlyingPirate module's loader setter: store the pointer handed over into
the module's small-data slot, return. That is the whole shape of this family, and the instruction
pair is byte-identical to the two nearest siblings already carved -
`src/MetroidPrime/ScriptLoader/Carve8021887C.c` (`SetLoader_Sandworm__FP18SSandworm_FuncPtrs`, 16
bytes below this range) and `src/MetroidPrime/ScriptLoader/Carve802188E4.c` (`fn_802188E4`,
DarkSamus's, another 32 bytes below), plus `Carve80200E3C.c` (SpacePirate's).

Every identification is measured, not recalled:

- **The name is retail's, so the unit is `.c`.** `symbols.txt:9472` carries the `fn_<offset>`
  placeholder, and the module imports that exact name:
  `strings build/G2ME01/FlyingPirate/FlyingPirate.plf | grep 80218A04` -> `fn_80218A04`. An alias
  would be a different symbol and the call would resolve to nothing.
- **Both call sites pass a plain pointer**
  (`build/G2ME01/FlyingPirate/asm/MetroidPrime/ScriptObjects/CFlyingPirateRel.s`): `RELExit` at
  0x00000570 (line 127) materialises `li r3, 0` - a null loader; `fn_22_5A4` at 0x000005C0
  (line 155) does `lis r3, lbl_22_bss_58@ha` / `stwu r0, lbl_22_bss_58@l(r3)` / `bl fn_80218A04`,
  so r3 holds the **address** of the module's own copy of the loader.
- **`lbl_22_bss_58` is `.bss:0x58`, `size:0x4 data:4byte`**
  (`build/G2ME01/FlyingPirate/asm/auto_05_00000000_bss.s:48-51`), so in *this* game the record the
  pointer addresses is only its first word - the loader itself. That is what
  `src/MetroidPrime/ScriptObjects/CFlyingPirateRel.cpp:162-168` already measures and spells as
  `lbl_22_bss_58 = fn_22_5D4; fn_80218A04(&lbl_22_bss_58);`.
- **The slot belongs to `FlyingPirate.cpp`, so this unit claims `.text` only.**
  `gLoader_FlyingPirate` is `.sbss 0x804193E8..0x804193F0` (8 bytes: the `value` pointer plus
  `SLoaderSlot`'s `padding` word), claimed and defined by
  `MetroidPrime/ScriptLoader/FlyingPirate.cpp` (`splits.txt:1633-1635`, definition at line 16),
  whose `.text` ends exactly at 0x80218A04. Its reader `LoadFlyingPirate` at 0x802189D8, the
  function immediately before this one, reads the slot with the same displacement this store writes
  (`lwz r6, -27032(r13)` at 0x802189E4) and calls member 0 of it (`lwz r12, 0(r6)`).
- **The parameter's type is retail's, from the other game.** `config/R3ME01/symbols.txt:2015` and
  `config/R32J01/symbols.txt:2012` both carry
  `SetSFlyingPirate_FuncPtrs__FP22SFlyingPirate_FuncPtrs`, 0x8 bytes - the same function in Prime 1,
  with a name. So the tag below is retail's, not invented. The store is one word for any pointer
  type and nothing in this unit reads through the parameter.

## What this run measured that is reusable

**1. `tools/carve_diff.sh` says NOT byte-exact for a carve that *is* byte-exact, whenever the
store is an `@sda21` small-data reference.** Run against the relocatable object it prints

```
retail: 2 instructions, 8 bytes
ours  : 2 instructions, 8 bytes
  +0   retail: 80218a04 stw r3,-27032(r13) ours: 00000000 stw r3,0(0)
differing instructions: 1
NOT byte-exact
```

because `objdump -d` renders an unresolved `R_PPC_EMB_SDA21` displacement as `0(0)` and the script
does not apply the relocation - it was written for branches and absolute addresses. The verdict that
matters here is the linked DOL's sha1 plus `flip_test`, and both hold. `powerpc-eabi-objdump -dr` on
the object is the check to use instead:

```
00000000 <fn_80218A04>:
   0: 90 60 00 00   stw  r3,0(0)
          0: R_PPC_EMB_SDA21  gLoader_FlyingPirate
   4: 4e 80 00 20   blr
```

`powerpc-eabi-nm` on the same object: `T fn_80218A04` (unmangled, as the `.c` rule requires) and
`U gLoader_FlyingPirate` - the symbol defined exactly once, in `FlyingPirate.cpp`.

**2. In this family the parameter tag can come from Prime 1's own mangling even when this game's
caller passes something narrower.** For Sandworm (`Carve8021887C.c`), DarkSamus
(`Carve802188E4.c`) and SpacePirate (`Carve80200E3C.c`) the module hands over the address of a
0x1C-byte `SFoo_FuncPtrs` record. Here it hands over the address of a 4-byte loader, so
`CFlyingPirateRel.cpp` spells the parameter `FScriptLoader*` while retail's Prime 1 name says
`SFlyingPirate_FuncPtrs*`. The store is one word either way and no register is touched differently,
so the retail tag was used and the discrepancy is written down in the file header rather than
papered over. Nothing in the object distinguishes the two, which is the honest statement: this
function cannot tell a record from its first word.
