## What it is

`rstl::construct`'s per-element **null guard**, copy half: `if (self != 0) { callee(self, src); }`.
The body is the twin's spelling verbatim, because the twin is measured:

- **`fn_80004D5C`** (0x80004D5C, `size:0x28`, `symbols.txt:98`, `Matching` 100.00% in
  `src/MetroidPrime/Player/CGameStateBlockConstruct.cpp:12-16`): ten instruction words, the **only**
  difference being the `bl` at offset 0x14 — `4b ff fd 31` → `fn_80004AA0` there,
  `48 00 00 15` → `fn_80256278` here.
- **`fn_801FEE60`** (0x801FEE60, `ScriptObjects/Carve801FEE40.c`, `Matching` 100.00%) and
  **`fn_801FEC84`** (0x801FEC84, `ScriptObjects/Carve801FEC64.c`, `Matching` 100.00%): both byte-exact
  here, **`bl` word included**, because in all three the callee sits 0x14 bytes past its own `bl`
  (0x80256264+0x14 = 0x80256278, 0x801FEE74+0x14 = 0x801FEE88, 0x801FEC98+0x14 = 0x801FECAC).

**The callee, read off bytes outside the claim.** `fn_80256278` (0x74 = 116 bytes, 29 instructions,
`asm/auto_03_80255D2C_text.s:406-437`) is a **copy constructor for a 0x2C-byte element**:
`bl fn_802562EC` (0x84 bytes, the base half), then `lha/sth` a short at +0x10 and six `lfs/stfs`
float pairs at +0x14..+0x28 out of `r31` into `r30`, `mr r3,r30` before the epilogue.

**The element size 0x2C is measured from retail's own caller.** `fn_802561F8` (0x802561F8, 0x38,
unclaimed, directly in front of the claim) is a push-back: `mulli r0,r5,0x2c` at 0x8025620C,
`addi r5,r5,1` + `stw r5,0x4(r3)` at 0x80256214 (the count), `add r3,r6,r0` at 0x80256218
(`mItems` at +0x0C plus index×stride), then one `bl fn_80256230`. 44 bytes = `sizeof(T)`.
`fn_80256230` (0x80256230, 0x20) is a frame and one `bl fn_80256250`, i.e. retail's `construct` for
that element — so this claim is the guard beneath it and the claim stops exactly where
`fn_80256278` begins. **No byte of this claim reads a member**, so the pointers are `void*` and
nothing is asserted about the class.

## Notes

- The **unit-boundary cycle** the carve vein warns about (an `auto_*` range that starts exactly
  where a neighbouring `Matching` unit's `.text` ends) does **not** bite here: `auto_03_80255D2C_text`
  does start exactly at `Carve80255C54.c`'s end (0x80255D2C), and `configure.py` + ninja still came
  through clean. Carving from a range adjacent to an existing carve boundary is fine; the failing
  case was adjacent to a **non-carve** unit boundary. Worth knowing, not worth a `NEW:` item.
- `docs/HANDOFF.md`'s state block (3 lines: matched/linked/DOL units) is the only edit I did not
  make: `goal_check.sh`'s own `gate.sh` run rewrites it under `MP_GATE_DOCS_WRITE=1`, as it does for
  every goal item. Nothing else outside the five files above changed.

No blockers, and nothing filed as `NEW:` — the item is complete.
