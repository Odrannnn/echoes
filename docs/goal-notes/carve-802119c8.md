## The two facts worth keeping (measured, not recalled)

**1. `-lang=c` is what keeps the symbol unmangled, and `probe_cc.sh` alone cannot tell you.**
`tools/probe_cc.sh` hardcodes `-lang=c++` (it was written for a `.cpp` unit), so compiling the new
source with it yields `T fn_802119C8__FP14SCarve802119C8i` — the bytes are already
`BYTE-EXACT`, but the name is mangled and objdiff would pair nothing. Re-run with the unit's real
flags (from `build.ninja`'s `cflags` line for a neighbouring `.c`, i.e. `cflags_retro` plus
`-lang=c`) and `powerpc-eabi-nm` prints exactly `00000000 T fn_802119C8`. **A carve's first
compile check must use `-lang=c`; `probe_cc.sh`'s `BYTE-EXACT` alone is not enough to claim the
symbol is right.**

**2. The receiver is the second argument of a reader, and its class is not this file's to
restate.** The one caller on the disc is `fn_80212EB0` (0x80212EB0, `auto_03_80212A2C_text`):
it keeps a read pointer at `+8` of its *first* argument (`lwz r3,0x8(r3) / addi r0,r3,4 /
stw r0,8(r26) / lwz r3,0x0(r3)`), checks the word it read against `0x54524545` ("TREE") and
then, on a match, reads the next 32-bit word and calls `fn_802119C8` with **`r27` — its own second
argument** as the receiver (`0x80212EE8 mr r3,r27` .. `0x80212EF8 bl fn_802119C8`). So the value
is an `int` and the receiver is the object being read into. The same receiver also owns the
