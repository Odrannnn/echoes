# carve-8028032c — `fn_8028032C` → new `Matching` unit `GuiSys/Carve8028032C`

Carved the one seeded function out of the unclaimed dtk range `auto_03_802802B8_text`
(0x802802B8..0x80280338) as its own plain-C `Matching` unit. The unit flips; the judge passes.

## What the range is

`config/G2ME01/symbols.txt:11232` carries the only name retail gives this code:

```
fn_8028032C = .text:0x8028032C; // type:function size:0xC align:4
```

`build/G2ME01/asm/auto_03_802802B8_text.s:49-54` is the dtk disassembly of the whole unclaimed
range, and its last function is the 12 bytes the item names:

```
# .text:0x74 | 0x8028032C | size: 0xC
.fn fn_8028032C, global
/* 8028032C 0027D12C  3C 60 42 4D */  lis r3, 0x424d
/* 80280330 0027D130  38 63 54 52 */  addi r3, r3, 0x5452
/* 80280334 0027D134  4E 80 00 20 */  blr
```

The returned word is `(0x424d << 16) | 0x5452` = **0x424D5452**.

## The twin, and what it does and does not tell us

The seed's twin is `CAuiMeter::GetWidgetTypeID() const` at 0x80274090, **matched**,
`build/G2ME01/asm/GuiSys/CAuiMeter.s:76-80`:

```
# CAuiMeter::GetWidgetTypeID() const
/* 80274090  3C 60 4D 45 */  lis r3, 0x4d45
/* 80274094  38 63 54 52 */  addi r3, r3, 0x5452
/* 80274098  4E 80 00 20 */  blr
```

Identical instruction shape and identical low half; only the `lis` immediate differs
(`0x4D45` vs `0x424D`). The matched twin is written `return 'METR'`
(`include/GuiSys/CAuiMeter.hpp:13`), and mwcc's multicharacter constant packs first character
into the most significant byte, so `'METR'` = 0x4D455452 — which settles the packing order.

**But `0x424D5452` is not a FourCC** (`'BMTR'` under that order), and retail names this function
nothing. So the twin only justifies the *shape*, not the reading: I wrote the constant as an
`unsigned int` literal rather than as a multicharacter or `FourCC` expression, and said so in the
source. Nothing here is evidence that this returns a widget type ID, and the file does not claim
it does.

### Directory: `GuiSys`, and the link-order question

The nearest claimed range below is `GuiSys/CAuiImagePane.cpp` (0x8027EF10..0x802802B8); this
address is **0x74 bytes past its end**, in the same neighbourhood. The item's target is
`GuiSys/Carve8028032C`, which agrees, so no judgement call was needed.

`docs/RUNNING_THE_DECOMP.md` §"The carve vein" records that a carve starting exactly where
another unit's `.text` ends can fail `dtk dol split` with a link-order cycle. This one starts
0x74 bytes into the unclaimed gap, not on a boundary, so the cycle does not apply — and the build
confirms it: the split and the link both succeeded on the first try.

### Descending declaration order

One function, so descending order is vacuous here — `python3 tools/check_decl_order.py --unit
GuiSys/Carve8028032C.c` reports `0 unit(s) checked, none emits its functions out of retail order`,
i.e. the tool has nothing to compare for a single-function unit. Recorded so a later run does not
read that "ok" as a check it performed. The `flip_test` PASS below is what actually proves the
`.text` is not permuted. The source says the order must stay descending if a second function is
ever added.
