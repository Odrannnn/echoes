## What the two functions are

Neither is named by retail (`config/G2ME01/symbols.txt:10202-10203`, both `fn_<addr>`
placeholders), so both are byte-shape twins of already-matched code, copied under the `fn_` name.
The instructions are dtk's own, `build/G2ME01/asm/auto_03_8023E5F4_text.s:3452-3478`, read while
the range was still unclaimed.

- **`fn_8024143C`, 0x3C = 60 bytes, 15 instructions** - `__dt__5CMainFv` (0x800087DC,
  `src/MetroidPrime/main.cpp:517`, `CMain::~CMain() {}`) word for word: `mr. r31,r3 / beq` guards
  the receiver, `extsh. r0,r4 / ble` re-tests the flag as a **short** (a `bool` would give
  `extsb.`), `if (flag > 0)` is **inside** `if (self)` so the receiver's `beq` lands on the
  epilogue, and the epilogue's `mr r3,r31` is what says the return is `void*` - as `void` mwcceppc
  drops the move and the body is 14 instructions / 56 bytes, 12 short of the claim. The one call is
  `bl Free__7CMemoryFPCv`, so `Free__7CMemoryFPCv` (0x802CE388, `symbols.txt:12992`, 0x64) is
  declared `extern` and never defined: it is claimed by `Kyoto/Alloc/CMemory.cpp` in the DOL and
  defined for the host by `src/Kyoto/Alloc/PortMwccNew.cpp`, so this unit adds no undefined symbol.
- **`fn_80241478`, 0x10 = 16 bytes, 4 instructions** - `fn_8023E5E4`
  (`src/MetroidPrime/ScriptLoader/Carve8023E5A8.c:130`, 0x10, the two-float zeroing constructor)
  **byte for byte, the `lfs` included**. `lfs f0, lbl_8041DCB0@sda21(r0)` ; `stfs f0, 0x0(r3)` ;
  `stfs f0, 0x4(r3)` ; `blr` - one load, two stores, no frame. The encodings are the same word:
  `c0 02 b8 f0`, D = `0xB8F0` = -18192, and `_SDA2_BASE_` = 0x804223C0 (`tools/sda.py`) minus
  0x8041DCB0 is 0x4710 = 18192. Same object, same address, same `sda21` displacement.

This is written the same way as the same-shaped carves `Carve8023C860.c`, `Carve8023C950.c`,
`Carve8023E5A8.c`, `Carve80241C90.c` and `Carve802420F8.c` in this directory - the `void*
f(void*, short)` signature and this exact five-line body appear in many units of the tree, so the
identifying is already done and needed no fresh evidence.

## Who calls them, and with what

All four call sites are in `fn_800FF648` (`symbols.txt:4530`, 0x800FF648, 0x2C0 = 704 bytes), in
dtk's unclaimed `auto_03_800FF298_text` - `auto_03_800FF484_text` is the same code listed in the
other unclaimed range - so nothing of ours needs either function and no count depends on them.

- 0x800FF680 / 0x800FF688: `addi r3,r26,0x44` / `addi r3,r26,0x50` ; `bl fn_80241478`, in the
  prologue immediately after `bl __ct__20SLdrEditorPropertiesFv` on `r26 = r1+0x34` and
  `bl Green__6CColorFv`. Two calls on `this+0x44` and `this+0x50` inside a constructor's own body
  is a two-float member zeroed in place, not a load from data.
- 0x800FF8D4 / 0x800FF8E0: `mr r3,r29` / `mr r3,r28` ; `li r4,-1` ; `bl fn_8024143C`, the
  destructor walk at the end of the same function, immediately before
  `addi r3,r1,0x34 ; li r4,-1 ; bl __dt__20SLdrEditorPropertiesFv` on the same object. `-1` is
  MWCC's "destroy, do not free me afterwards", so the free-through-to-self is dead at both sites
  and is not dead in the source.

## The one data reference, and why this file does not define it

`lbl_8041DCB0` (0x8041DCB0, `.sdata2`, `size:0x4`, `data:float`, `symbols.txt:24608`; dtk recorded
`.float 0` at `build/G2ME01/asm/auto_11_8041DAC8_sdata2.s:567-570`) is retail's own pool entry. It
needs **no host definition here**: `src/MetroidPrime/ScriptLoader/Carve8023E5A8.c:124` already
defines it under `#ifndef __MWERKS__`, in the same build of the same target, so the name resolves
for the port link. **Repeating that definition would have been a second definition of one symbol in
the flat link** - invisible to `link_gap.py` (it counts what is *missing*) and to the boot probe
(it links with the reach stubs); `tools/gate.sh`'s `port link dups` step is what catches it. This
file declares the symbol `extern const float` and never defines it.

**No `PortLinkStubs.cpp` edit was needed.** Measured: `grep -rn "fn_8024143C\|fn_80241478" src/
include/` over the clean tree returns nothing, so neither name had a host definition to remove -
unlike `Carve80241C90.c`, whose claim removed a `#ifdef TARGET_PC` stand-in for `fn_80241C90` out
of `Carve80220394.c`. Listing this unit therefore *resolves* two names for the port link and adds
none; `goal_check.sh`'s `gate.sh` line covers `port link gap` and `port link dups`.
