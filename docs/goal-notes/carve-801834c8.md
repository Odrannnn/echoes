The last row is the whole lesson and it is a codegen rule, not a semantic claim: a non-POD
element has a non-trivial copy constructor, which is what retail's own `CRuleValue` has and what
`uninitialized_copy`'s placement `new (dest) T(src)` then lowers to retail's `cmplwi r4,0 / beq /
lwz / stw / lwz / stw`. The POD spelling skips that and the allocator shifts everything up one
register. `include/rstl/construct.hpp:36-42` already records the same effect for `unsigned long
long` ("the primary template above says false, so `destroy_impl(begin, end)`'s loop survives …
and the copy constructor's loop is unrolled eight elements per iteration"), from the other side.

does not repeat them: `newData` declared before the capacity test; `mItems`/`mCount` cached in
locals (costs r27/r28 and grows the frame to `stmw`/`lmw`); `destroy(begin(), end())` instead of
`destroy(mItems, mItems + mCount)` (frame grows to 0x40, four more home slots); the body in a

`mAllocator.allocate` / `mAllocator.deallocate` instead of the free calls; `allocate2<T>`; the

## Notes worth keeping

- **A carve written as plain C is not always a carve that can flip.** The item's recipe assumes
  hand-rolled structs and declared externs, and for a destructor chain (the `Carve800045A0.c`
  shape) that is right. For anything that goes *through* `rstl`'s own templates it is not: the
  by-value `pointer_iterator` copies `begin()`/`end()` make are four instructions of frame stores,
  and no amount of re-spelling a local struct recovers them. Read the twin's source and use the
  same headers when the twin is a template instantiation.
- **POD-ness is a register-allocation lever under MWCC, and it is measurable.** Same two words,
  same 0xD4 length, 15 instructions different, and one `struct` header fixes it. This is the same
  mechanism `docs/RUNNING_THE_DECOMP.md` records as the `rc_ptr` r3 finding and the `IsAllocValid`
  operand-order finding: the register a value lands in is a function of how the expression is
  written, not of what it computes.
- **`tools/carve_diff.sh` reads `build/G2ME01/main.elf`, which is your own build.** Once a unit is
  in the link the "retail" side of that comparison is your own bytes, so it cannot tell you
  anything; and `build/G2ME01/asm/auto_*` loses the range the moment `splits.txt` claims it. Read
  retail out of the disc with `python3 tools/dol_read.py <addr> <size>` instead, as
  `docs/goal-notes/carve-801fd52c.md` does.
- **`link_check`'s "N symbols this change ADDED" is not the growth**; the gate is the **count**
  line against `build/goal/judge/undef.base.count`.
