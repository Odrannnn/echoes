per 0x20-byte element two words at +0 and +4, **five** `lfs`/`stfs` pairs at +8/+0xC/+0x10/+0x14/

element is `{word, word, float[5], byte, byte}` = 0x20 bytes with natural tail padding - **not**
six floats, as runs one and two said.  `Carve80044D48.c` spells that out and says so.

**New this run, and it is an inference rather than a measurement: `N` is almost certainly 11.**
`fn_80044D90` is the copy constructor of the 0x164-byte element, it copies nothing but the count
and the element array, and `4 + 11 * 0x20 == 356 == 0x164` - so one `reserved_vector< Elem, 11 >`
accounts for the whole object, and any other reading needs a second member that the copy
constructor never touches.  The source declares `mData[11]` and says in its own comment that the
value is a consequence, not a measurement; nothing in the claim's codegen depends on it (the
array is never indexed).  The **outer** `N` (how many 0x164-byte elements) is still unknown:
`fn_80044CA4` is called once, from 0x80044064 in `__ct__13CStateManagerF...` with
`addi r3,r31,7832` (= `+0x1E98`) and `li r4,4`, so the container holds 4 elements, but `4` is the
