## The one thing that was not obvious: `fn_80255984`'s parameter convention

This is the wall, and it is worth recording because the obvious spelling fails and the twin's spelling
works for a reason the twin's own header only half-explains.

Written the obvious way — `fn_80255984` taking `SCarve80255900Iterator` **by value**, caller passing
`first, last` — it scores **10/33 and 1/14** with a **48-byte frame against retail's 32**. By-value
forces a copy that spills two extra slots. Declaring the iterator locals as that struct type instead
of `unsigned char*` scores **9/33**. Retail's own bytes say what it wants: `lwz r5,0(r4)` /
`addi r4,r1,8` / `lwz r0,0(r3)` / `addi r3,r1,12` is each argument **dereferenced into a frame slot**,
and the address of that slot is what the `bl` passes on.

So `fn_80255984` takes `const void*` and casts, and `fn_80255900` passes `&first` / `&last` of plain
`unsigned char*` locals. That is **33/33 + 14/14 + 20/20, 67 instructions, frame 0x20** — byte-exact.
This is the same trick `ScriptObjects/Carve801FD998.c` uses for its `fn_801FDA1C`; the comment there
calls the arguments "the address of a caller frame slot", and that phrase is the whole mechanism.
Written into the new file's header as a measured claim, not as a copy.

## Two things that cost time, and one that is not what it looks like

**1. `tools/carve_diff.sh` on an unlinked `.o` always reports the `bl` words as differing.** Five
`bl`s carry relocations until the link fills them in, so `NOT byte-exact` on a correct carve is
expected — the already-`Matching` neighbour `Carve80255A0C.o` reports the same 6. Compare
`build/G2ME01/**src**/X.o` — the intermediate, not `build/G2ME01/**obj**/X.o`, which `dtk dol split`
produces from the *linked* DOL. Only `flip_test.sh` decides.

**2. `build/G2ME01/asm/<unit>.s` is `dtk`'s listing of the linked DOL, not our compile.** After a
failed link it still shows retail's bytes for the unit, so it will happily confirm a source that
does **not** compile to them. It cannot establish what retail had; read `objdump` of the object, or
the `src/` intermediate, for that.

**3. A build that reports `main.dol: FAILED` with every REL also FAILED is usually stale ninja
state, not 87 broken modules.** `dtk dol split` writes `build/G2ME01/obj/**` and `asm/**`, and ninja
will not rerun it on its own; `build/G2ME01/report.json` then fails with `Failed to open
./build/G2ME01/obj/<unit>.o`. `rm -f build/G2ME01/config.json build/G2ME01/ok` forces both. I lost
time reading that as a codegen failure when the object was fine.
