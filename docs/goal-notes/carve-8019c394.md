## The three things that had to be right, and what each one cost

**1. Both copies are shifted one integer register against their twins, and both need a leading
unused pointer parameter.** `fn_8019C394` is a byte-shape twin of
`CBSLocomotion::ComputeWeightPercentage` (`src/MetroidPrime/BodyState/CBSLocomotion.cpp:136-144`,
retail 0x800F4864) and `fn_8019C3E4` of `CBSLocomotion::Shutdown(CBodyController&)`
(`:73`, retail 0x800F4C28). The twins are *members*: `this` in `r3`, explicit arguments from
`r4`. These copies read `a` out of `r4` and `b` out of `r5` and never touch `r3`, and
`fn_8019C3E4` forwards `r4` - not `r3` - as the callee's `this`. Written with the twin's own
signature the loads land on `r3`/`r4` and there is **no `mr r3,r4` at all**: `fn_8019C3E4` came
out 29 instructions / 116 bytes against retail's 10 / 40. Adding the unused first parameter
produces the `mr` and the exact size. The item's reason only mentions `fn_8019C3E4`'s `mr`; the
same shift is what puts `fn_8019C394`'s loads on `r4`/`r5`, and I only found it because
`carve_diff` still disagreed after the frame matched.

**2. The `.sdata2` words have to be `extern`, not literals.** `lbl_8041CB6C` = `3F800000`,
`lbl_8041CB70` = `00000000`, `lbl_8041CB80` = `34000000` (= 2^-23), read out of
`build/G2ME01/main.elf` at `.sdata2` VMA 0x8041A3C0 / file offset 0x3C3C20 - the same three
values the twin pools at `lbl_8041B8D4` / `lbl_8041B8D0` / `lbl_8041B8E8`. They live in
`auto_11_8041CB40_sdata2.o`, a retail split object that is already in the DOL link, so
`extern const float` + use emits exactly `lfs ..., lbl_8041CBxx@sda21(r0)` with the retail name -
the same arrangement as `CAi.cpp`'s `extern const float kCAiSplashDenom`, and that unit is
`Matching`. **Reading the values off the split object's own `.sdata2` is misleading**: I did
that first and got `lbl_8041CB80 = 0x3e99999a`, because the symbol's section offset is not its
address minus the section VMA when the split object carries the whole run. Read
`build/G2ME01/main.elf` instead; it gives `34000000`.

**3. `extern const float`, not `extern float`, is what puts the rate load in retail's slot.**
`fn_8019C3E4` loads the rate between `mflr r0` and `stw r0,0x14(r1)`, ahead of the `mr r3,r4`.
With an unqualified `extern float` mwcceppc emits the same ten instructions with the `lfs` one
slot *later*, after the frame store. With `const` it schedules the load where retail has it.
Measured, both, in `build/G2ME01/src/MetroidPrime/Carve8019C394.o`. A literal `1.f` also
schedules it correctly - which is why the `extern` was worth keeping for the other reason in (2),
not for this one.

## Lessons worth keeping (not `NEW:` items)

- **A byte-shape twin's *argument registers* need not match the twin's, and the item's reason
  does not always mention it.** The twins are members and the copies are not; both copies here
  start their pointer arguments at `r4`. Check the `lfs`/`lwz` base registers against the
  twins' and count the leading unused parameter before concluding the body is wrong.
- **`extern const` is schedulable, `extern` is not.** Same ten instructions, one slot out.
  This is the same family as the documented `rc_ptr`/operand-order findings in
  `RUNNING_THE_DECOMP.md`'s carve vein: *how the expression is written* decides the schedule.
- **Reading a `.sdata2` word's value out of its `auto_*` split object can be off**; the object's
  section offset is not the address delta once the split carries a whole run. `main.elf` is the
  ground truth.
- A carve whose body loads retail constants must define them for the host **in the carve file**.
  `Carve80003858.c:53-56` accepted the gap growth and a raised baseline; a lane that cannot raise
  the baseline cannot do that.
