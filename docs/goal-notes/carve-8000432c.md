## Two things that had to be measured, not guessed

**1. The `fn_800043B0`/`fn_800043E8` pair is passed as pointers, and that is what the four `stw`
are.**  Both take their two iterators **by value**, and MWCC passes a class-type by-value argument
as a pointer to a caller-side temporary.  So `fn_8000432C`'s `fn_800043B0(self->begin(), self->end())`
needs a temporary for each `begin()`/`end()` result *and* a second one for each parameter: the four
`stw rX,0x8/0xc/0x10/0x14(r1)`, and the argument registers `addi r3,r1,0x14` / `addi r4,r1,0xc`
are the second pair.  Writing it through named locals instead
(`It b = self->begin(); It e = self->end(); fn_800043B0(b, e);`) gives the **same 132 bytes** but a
different frame - the parameter copies land at +0x08 and +0x0C - and the DOL does not match.  Both
spellings were measured; only the call form is byte-exact, and the source uses the call form, as
`include/rstl/vector.hpp:139-142` writes it.

The `T* const last` local inside `end()` is also load-bearing: it is why retail reads the buffer
**twice** (`lwz r5,0xc(r30)` at 0x80004354 and `lwz r0,0xc(r30)` at 0x80004368).  Remove it and
the two reads collapse into one and `fn_8000432C` is 4 bytes short.

**2. Declaring the functions in ASCENDING order permutes `.text` and only the flip catches it.**
This cost the one real iteration of the run.  The first build with all four files in place
compiled, objdiff reported 100.00% per function, `size` said `.text 0x10C`, `nm` showed the three
symbols and nothing else - and the DOL still differed, in exactly 201 bytes.  The cause was that
the three definitions were written top-down as `fn_8000432C`, `fn_800043B0`, `fn_800043E8`:
mwcceppc emits definitions in **reverse** source order, so the object came out
`fn_800043E8`, `fn_800043B0`, `fn_8000432C` and the linker placed `destroy_impl` where the
destructor belongs.  Confirmed by disassembling the linked `build/G2ME01/main.elf`, which showed
`8000432c <fn_800043E8>`.  Reversing the three definitions fixed it; `nm -n` on the object then
reads `fn_8000432C@0`, `fn_800043B0@0x84`, `fn_800043E8@0xbc`, ascending, and the DOL sha1 matches.
`tools/check_decl_order.py --unit main/MetroidPrime/Carve8000432C` is clean, and the gate's
`decl order` step passes.  **Worth noting for the next lane: the item's own advice to check
`check_decl_order.py` before promising a promotion is not optional - but it also did not fire here
(it reported `0 unit(s) checked`, because the unit is not in `report.json` until a build has
produced it), so the DOL hash was the only detector.**
