## Why the file is `.c`, and what the pointer is

`symbols.txt:10088` gives the retail name `fn_802399F4 = .text:0x802399F4; // type:function
size:0x8 align:4`, so there is nothing better to call it, and
`strings build/G2ME01/RubiksPuzzle/RubiksPuzzle.plf | grep 802399` returns `fn_802399F4` — the
**RubiksPuzzle module (module 4) imports that exact name from the DOL**, so it cannot be renamed or
aliased. A `.cpp` definition would mangle; a `.c` unit is compiled `-lang=c`, so the definition *is*
the symbol.

Both of the module's two call sites (`build/G2ME01/RubiksPuzzle/asm/auto_00_00000000_text.s:413`
and `:441`) pass a plain pointer, which is what the parameter type is:

- `RELExit` at `.text:0x538` materialises `li r3, 0x0` first (line 411) — a null loader, as in
  every other module of this family.
- `fn_4_57C` at `.text:0x57C` is the module constructor: `lis r3, lbl_4_bss_0@ha` (line 437) and
  `stwu r0, lbl_4_bss_0@l(r3)` (line 440) put the module's own loader into its one-word `.bss`
  cell, then hand **the cell's address** over. `build/G2ME01/RubiksPuzzle/asm/auto_05_00000000_bss.s`
  gives `lbl_4_bss_0 size:0x4 data:4byte` and it is the only object in the module's `.bss`.

So the record type in the file is named for the parameter only, matching the convention already
established by `Carve80235DCC.c:84-89` and `Carve80200E3C.c:56-65`: MWCC does not encode a
variable's type in its name, so the `extern` resolves to `gLoader_RubiksPuzzle` itself whatever the
type is spelled, and nothing in this unit reads through the pointer.
