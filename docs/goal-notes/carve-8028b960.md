## The two codegen rules this cost the most time

**1. `const` on a callee's pointer parameter moves a `lwz`.** The one change that made
`fn_8028BA18` byte-exact was spelling its first parameter `const struct SCarve8028B960Iterator*`
rather than `struct SCarve8028B960Iterator*`. With it, mwcceppc emits retail's order —

    stw r31,0x1c / lwz r31,0x0(r3) / stw r30,0x18 / mr r30,r5 / stw r29,0x14 / mr r29,r4

— i.e. the cursor load sits **between** the r31 and r30 spills. Without the `const`, the load is
identical but sits after both argument copies (`mr r30,r5`, `mr r29,r4`), which is 3 instructions
out of place. Six spellings of the body (a `char*` cursor, an `unsigned char*` cursor, one
declaration statement, `(*begin).p`, `*(const char**)begin`, `begin->p`) all produce the late load;
only the `const` moves it. Worth trying on the other hand-written C carves with a load hoisted out
of retail's position.

**2. A stack array defeats dead-store elimination; named locals do not.** Retail's
`fn_8028B960` hands `uninitialized_copy` four stack words - the two one-word iterators at `r1+0x14`
and `r1+0x0C` and two dead copies of the same two pointers at `r1+0x10` and `r1+0x08` - and all four
stores are in its bytes. In C, four named locals holding those values compile to **two** stores:
mwcceppc removes the two stores nothing reads. `struct It its[4]` written element by element keeps
all four, because the array's address is taken for the call. This is how the four stores below are
reachable at all, and it is the first thing to try on any carve that needs a redundant store.

Also measured while matching `fn_8028BA18`: the loop must be a `for` whose increment clause is
`cur += 0x20, tmp += 0x20`, and `end` must be **re-read every iteration** (`lwz r0, 0(r29)` inside
the loop). Written as a `do { } while` mwcceppc sinks the load into the loop tail and drops
retail's `b .L_8028BA54`; written with `end->p` hoisted into a local it CSEs the load to a register
before the loop and compares registers (`cmplw r31, r31`). The `for` form with the end pointer
left in r29 reproduces the loop exactly.

## What `fn_8028B960` is, for whoever picks it up

0x8028B960, 0xB8 = 184 bytes, `rstl::vector<SAreaSurface>::reserve(int)`, twin of the matched
`reserve__Q24rstl49vector<12SAreaSurface,Q24rstl17rmemory_allocator>Fi` (0x8005F248,
`src/MetroidPrime/CGameArea.cpp`). Its bytes, read off `auto_03_8028B914_text.s:32-84`: return
unchanged when `newSize <= mCapacity` (`lwz r0, 8(r3)` / `cmpw r30, r0` / `ble`), else
`allocate__Q24rstl17rmemory_allocatorFi(newSize * 32)` (`slwi r3, r30, 5`), build the four iterator
words, call `fn_8028BA18` at 0x8028B9C8, walk the old buffer with a loop that **calls nothing** and
steps `addi r4, r4, 0x20` — that is `destroy(mItems, mItems + mCount)` for a trivially destructible
element, so the loop survives but its body does not — `Free__7CMemoryFPCv`, then store the new
pointer and the capacity. The tail from 0x8028B9CC on **is** reproducible in plain C: two locals and
a `while (cur != stop) cur += 0x20;`, and `fn_8028B960` matches it byte for byte from there down.
