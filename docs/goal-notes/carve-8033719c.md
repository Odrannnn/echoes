# carve-8033719c — `fn_8033719C`, the vtable slot that returns `.sdata2` word 0 — Matching

`kind: match`, target `Kyoto/Math/Carve8033719C`. Claimed exactly `.text 0x8033719C..0x803371A4`
(0x8 bytes, 1 function) out of dtk's `main/auto_03_8033719C_text`, which covers exactly that
range and nothing more (`build/G2ME01/asm/auto_03_8033719C_text.s` header:
`# 0x8033719C..0x803371A4 | size: 0x8`).

## What it is

```
# .text:0x0 | 0x8033719C | size: 0x8
/* 8033719C 00333F9C  C0 22 C9 78 */  lfs f1, lbl_8041ED38@sda21(r0)
/* 803371A0 00333FA0  4E 80 00 20 */  blr
```

Byte-shape twin of the matched `CParticleGen::GetGeneratorRate` at 0x800534BC
(`src/MetroidPrime/CExplosion.cpp:44`, `float ... { return 1.f; }`, retail
`lfs f1,lbl_8041A920@sda21(r0)` / `blr`). Same two instructions, same `f1`, differing only in
the 16-bit `@sda21` displacement because the two pool words sit at different addresses.

Displacement measured: `powerpc-eabi-nm build/G2ME01/main.elf` gives `_SDA_BASE_ = 0x8041FD80`,
so `0x8041ED38 - 0x8041FD80 = -0x1048 = 0xEFB8` → `C0 22 C9 78`. ✓

## The pool word is `0.0f`, and it stays with dtk

`build/G2ME01/asm/auto_11_8041EC28_sdata2.s`:

```
# .sdata2:0x110 | 0x8041ED38 | size: 0x4
.obj lbl_8041ED38, global
	.float 0
```

and `powerpc-eabi-objdump -s -j .sdata2 --start-address=0x8041ED30 build/G2ME01/main.elf` reads
`3a83126f 3f4ccccd 00000000 00000000`, so the word is `0x00000000` = `0.0f` (the second zero is
the pool's alignment pad for the `double` at 0x8041ED40).

## The thing that cost the run: this carve must NOT claim the `.sdata2` word

Two approaches were built and measured before the one that works.

**(a) Claim it, write `return 0.f;`.** Link fails outright — the retail *name* disappears from
the DOL because mwcceppc gives a bare literal a local pool name, and ten neighbouring auto
functions reference the word by name:

```
### mwldeppc.exe Linker Error:
#   undefined: 'lbl_8041ED38'
#   Referenced from 'fn_803371EC' in auto_03_803371A8_text.o
### mwldeppc.exe Linker Error:
#   undefined: 'lbl_8041ED38'
#   Referenced from 'fn_803378E0' in auto_03_803371F8_text.o
... 9 more (fn_8033788C, fn_80337844, fn_803377EC, fn_80337794, fn_8033762C, fn_8033758C, ...)
then:  #   Link failed.
```

**(b) Claim it, name the constant `lbl_8041ED38`.** That puts a global at the claimed address,
so the *name* resolves — but the **code** still does not load it. mwcceppc constant-folds the
read and points the `lfs` at its own pool copy, which lands 4 bytes later:

```
00000004 l     O .sdata2  00000004 @5           <- the relocation targets this
00000000 g     O .sdata2  00000004 lbl_8041ED38  <- the definition is here
RELOCATION RECORDS FOR [.text]:
00000000 R_PPC_EMB_SDA21   @5
```

`volatile const` does not help — the folding happens anyway. The DOL then came out **one byte**
wrong: `cmp -l` against a clean build of the same tree gives exactly one differing byte, at DOL
file offset 0x334A1F = `.text:0x8033719F`, the low byte of the `lfs` displacement —
`C0 22 C9 7C` (`0xEFBC`) where retail has `C0 22 C9 78` (`0xEFB8`). That is the
`lbl_8041C398` failure `src/MetroidPrime/PortGlobals.cpp:993` already records, and it is why the
twin is written `return 1.f` *inside a unit that already claims* the pool: **a carve may not
claim it.**

**(c) What works — declare, do not claim.** `extern const float lbl_8041ED38;` binds from dtk's
`auto_11_8041EC28_sdata2.o`; the displacement comes out `0xEFB8`, the ten neighbours keep the
name, this unit carries no `.sdata2` claim at all. Same pattern as `Carve8023E5A8.c`
(`lbl_8041DCB0`) and `Carve80229EAC.c` (`lbl_80419590`), including the `#ifndef __MWERKS__`
host-only definition so the port's flat link takes no new undefined symbol.

## Notes for the next run

- **Lesson, reusable across the carve vein:** for a carve whose body is `lfs f1, lbl_…@sda21`
  (or any SDA data reference), *declare* the retail data symbol; do not claim the `.sdata2`
  range and do not write the literal. The claim breaks the link by name (ten neighbours), and
  the named-constant spelling breaks it by address (constant folding puts the `lfs` on the
  compiler's own pool copy). This is not specific to this function.
- **Observed, not fixed (out of scope, not a `NEW:` item):**
  `src/MetroidPrime/PortGlobals.cpp:989` points at `MetroidPrime/Carve800534BC.c` as the unit
  that declares and loads `lbl_8041A920`, but no such file exists — the body is in
  `src/MetroidPrime/CExplosion.cpp`. A stale doc reference, nothing countable.
- **Not done, deliberately:** `fn_803371EC` (0x803371EC, 8 bytes) is the same two instructions
  with the same pool word and sits in dtk's `auto_03_803371A8_text`. It is a one-line carve of
  exactly this shape and would be `Kyoto/Math/Carve803371EC.c`. I did not take it: the item
  says claim this range and nothing else.
