## What was measured

Retail's `PostConstruct` (0x800BBC3C, 128 bytes, 32 instructions) is 16 dead `lwz r0, K(r31)`
loads at K = 0,4,...,60, then `bl AdjustTransformForType`, `addi r3,r31,16`,
`addi r4,r1,8`, `bl __as__12CTransform4f`. The loads' results are discarded, so retail is
mwcc's output for a loop whose body mwcc could not sink: 16 loads, **no stores at all**, which
is why the object looks like a partial unroll.

Our version emitted **14** loads — 0,4,8,12,16,20,24, then 32..56 — i.e. exactly the two 4-byte
holes at 28 and 60. `swap` was dead in 14/16 lanes; `mr r4,r31` landed at the slot after the
first load only when 15 loads were emitted, which is why the byte-level diff is a 2-instruction
skew rather than a mismatch. objdiff's 93.53% was exactly this.

The two holes are a **C++ aliasing artefact, not a code problem**: `dst[i] = f(src[i])` with
`dst == src` as two identically-cast pointers lets mwcc prove `p[i] = SwapBytes(p[i])` is a
self-assignment and drop the stores, then DCE the loads it can attribute to the dropped stores.
Giving the read side `const` stops that proof: mwcc must still perform the read.

### Spellings tried this run (all measured, none reached 100%)

| spelling | loads | bytes | verdict |
|---|---|---|---|
| baseline `reinterpret_cast<uint*>(this)` both sides, bound `offsetof(x40_)/sizeof(int)` | 14 | 120 | 93.53%, two holes at 28/60 |
| literal `i < 16` | 14 | 120 | same as baseline |
| `uint* p` local, `i < 16` | 14 | 124 | 15 loads but `mr r5,r31` extra -> skew |
| `int* p` local / `uint i` index / `p < this+16` walk / `uint* = &mType` / `i <= 15` / `const int n = 16` | 12-14 | 112-124 | worse; `!= 16`, `do/while`, `ptrdiff_t` i, `uchar*` stepping, byte-wise `memcpy` all stop unrolling (19-24 instrs, 0 loads in the window) |
| two *different* pointers (`const uint* src`, `uint* dst`) | 16 | 200 | correct 16 loads but keeps all 16 `stw` — stores not DCE'd, 72 extra bytes |
| plain `p[i] = p[i]` (no SwapBytes) | 0 | 64 | loop vanishes entirely |
| **`const uint*` read side, same bound as baseline** | **16** | **128** | **exact, 121/128 positional bytes; the 7 differ only in the two `bl` displacements that the linker fills** |

The winner is the last row, i.e. the *smallest* change from the baseline: the loop is unchanged
except that its source operand is `const`. That is the lesson worth keeping: on this unit
"dead" loop bodies are reproduced by making the read side `const`, not by restructuring.
