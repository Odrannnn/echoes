## What the source had to get right (three things, all measured)

**1. The loop is indexed, not an iterator.** Compiled both spellings with `tools/probe_cc.sh` on the
real body. Indexed: `li r31,0` / `li r30,0` in the prologue, `lwz r3,0xc(r28)` / `lwzx r4,r3,r31` /
`cmplwi r4,0` / `beq` / `addi r31,r31,4` / `addi r30,r30,1` / `lwz r0,0x4(r28)` / `cmpw r30,r0` /
`blt` - retail's 11 instructions, byte for byte. Iterator: hoists `mItems` into `r31`, has **no second
induction variable**, and ends on an end-pointer compare (`slwi`/`add`/`cmplw`/`bne`) - **4
instructions longer, never matches**. So `rstl::vector`'s `begin()/end()` is not an option here even
though it looks equivalent.

**2. `m_msg` is a four-character code.** `stw r5,0x24(r1)` = 0x58414C44 = `'XALD'`, built by
`lis r3,0x5841` / `addi r5,r3,0x4c44` - a constant in the instruction stream. The tree's
`EScriptObjectMessage` enumerators are all of that shape (`kSM_Load = 0x4c4f4144`), and
`CGameCollision` already spells one with `static_cast<EScriptObjectMessage>('XOND')`.

**3. Two passes, and the ten stores are one statement.** `mgr.DeliverScriptMsg(CScriptMsg(...))` is a
byte-shape twin of `CGameCollision::SendMaterialMessage` (retail 0x801255BC,
`CGameCollision.s:2261-2288`, `Matching` 100%) apart from the message code. It reproduces retail's
**ten** stores at the same offsets in the same order. The last five fit `CScriptMsg`'s 0x10-byte
layout exactly; the first five (`0x10, 0x8, 0xc, 0x14, 0x18`) are a second, unread copy - **what they
are is not established**, so the comment says so rather than guessing. What I did measure is that a
`const CScriptMsg msg` local gives a **byte-identical 96-byte object**, so the count does not come from
binding a temporary to the reference; the naive explanation (and the one I wrote first) was wrong.

Also fixed by the header rather than by guessing: `CScriptMsg`'s ctor takes `(unk, id, originator, ...)`
while its members are `m_unk, m_originator, m_id` (`CEntityInfo.hpp:317-319`), and the header says not
to tidy that back because mwcceppc keeps it. Here `m_unk` and `m_originator` hold the same value, so
**this function alone cannot tell the two orders apart** - `CGameCollision` plus this copy are what make
the spelling unambiguous, and the comment now says that instead of implying this unit proves it.

**Lessons for the next carve (not `NEW:` items - no code left to write).**
- A real-named function in a carve is not harder than an `fn_` one; it is the same recipe plus "write
  the member the header declares, by value if `symbols.txt` says `F`". `probe_cc.sh` on a 10-line body
  settles the loop/argument questions in a minute and the flip then has nothing left to decide.
- `rstl::vector` loops: **check indexed vs iterator with `probe_cc.sh` before writing a carve.**
  MWCC's iterator loop is 4 instructions longer and never matches; retail's indexed shape is exact.
- A `DeliverScriptMsg(CScriptMsg(...))` site is ten stores, and naming the message in a local does not
  change that. Do not "simplify" one of these call sites into a named local expecting the same bytes
  on different grounds - it happens to be byte-identical here, measured, but the reason is not known.
- `link_gap.py` is a **two-way** check: a symbol that is now *provided* fails the gate until its
  `port_link_gap_list.md` entry is deleted, and `check_docs_claims.py` then wants the
  `port_link_gap.md` table row too. Both files, same commit, or the item fails on a docs step.
- **A carve that adds a file to `files.cmake` is a port change.** `files.cmake` is one of the four
  carve files and it is the one the port build reads, so it is not bookkeeping.
