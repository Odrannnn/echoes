## The item's `reason` was wrong about `.c`, and that is the whole item

The reason says "plain C so the fn_ names do not mangle" and names `src/MetroidPrime/Carve8000387C.c`.
**I wrote the `.c` first, and it cannot reach 100%** - this is a measured wall, not a preference, and
it is the same wall `src/MetroidPrime/Carve801EF84C.cpp:51-63` already records for the identical
twin.

Plain C, the same logic as `include/rstl/vector.hpp:127-136` written out over a hand-declared
`struct SPairVec` and a hand-written block loop, is **49 to 51 instructions off**, and three of the
four spellings are also four bytes long. Every difference is register assignment, in one place:
retail loads the count straight into **r3** and derives both halves of its unroll from it
(`lwz r3,0x4(r30)` / `srwi. r0,r3,3` / `andi. r3,r3,7`), while every C spelling measured puts the
count in **r0** and then shuffles it into r3 with an extra `mr r3,r0` at the loop head, which
cascades into a different register for the destination pointer (r6 instead of r4).

Spellings measured this run, none byte-exact. "ours" is the object's `fn_8000387C`; retail is
82 instructions / 328 bytes:

| spelling | ours | differing instructions |
| --- | --- | --- |
| block copy into a local `items`, `self->mItems = items;` after it, then `while (remaining != 0) { *cur = *it; --remaining; ++it; ++cur; }` | 82 insn / 328 B | **49** |
| `self->mItems = allocate(...)` written straight to the member, then `while (remaining != 0) { *cur = *it; --remaining; ++it; ++cur; }` | 83 insn / 332 B | 51 |
| same, `for (remaining = self->mCount; remaining != 0; --remaining, ++it, ++cur)` | 83 insn / 332 B | 51 |
| same, `for (remaining = self->mCount, cur = self->mItems; remaining != 0; --remaining, ++it, ++cur)` | 83 insn / 332 B | 51 |

The first row is the closest and is worth knowing about: it is the **right length** - 328 bytes, so
`unit_fit.sh` would have called it a fit - and still 49 instructions off, which is the reminder
`docs/PROCESS_LESSONS.md` makes about a check that cannot fail. The extra `mr r3,r0` the other
three pay is one instruction each; the other 48 differences all follow from that one register.

`rstl::uninitialized_copy_n` (`include/rstl/construct.hpp:140-150`) takes the count as its **second**
argument, and that is what carries it in the register retail uses - `Carve801EF84C.cpp:55-57` states
it, and `src/MetroidPrime/Player/CGameStateBlockCopyCtor.cpp:8-16` had already found it for the
byte-element instantiation. So the body has to be written against the real headers, which needs
C++, and C++ mangles `fn_8000387C` to `_Z<len>fn_8000387Cv` unless the definitions are wrapped in
`extern "C"`. **`extern "C"` in a `.cpp` is the only spelling that satisfies both requirements**, and
it is already the arrangement this tree uses for Matching carves of this exact shape
(`Carve801EF84C.cpp:88`, `Player/CGameStateBlockCopyCtor.cpp:34`). The file is therefore
`src/MetroidPrime/Carve8000387C.cpp`, not `.c`.

Two further C forms were measured by the lane that wrote the twin and are recorded in
`Carve801EF84C.cpp:58-63` so they are not repeated: the same loop as a three-argument `static` /
`static inline` helper with and without `const` on the source. Neither reaches 100 either, and the
two that do keep the count in r3 do it by **outlining** the helper, which puts a third function in
the object and breaks `tools/unit_fit.sh` - so the helper spelling is not available here.

## The bodies and the twins they came from

Both were measured against an already-`Matching` function in this tree before a word was written,
with `powerpc-eabi-objdump -d` over our object and over `build/G2ME01/main.elf`:

- **`fn_8000387C`** vs `fn_801EF8B8` (0x801EF8B8, 0x148, `src/MetroidPrime/Carve801EF84C.cpp:144`).
  Two 656-hex-digit streams; they differ **only at hex offsets 162-167, i.e. instructions 20-21** -
  the `bl allocate__Q24rstl17rmemory_allocatorFi` at 0x800038CC and the `stw r3,0xc(r30)` that
  follows it, i.e. exactly the callee displacement and the register the call returns into. Every
  other instruction word is identical.
  It is `rstl::vector< rstl::pair< uint, uint >, rstl::rmemory_allocator >::vector(const vector&)`,
  `include/rstl/vector.hpp:127-136`. The bytes say so themselves: `lwz r0,0x8(r4) / lwz r3,0x4(r4)`
  then `stw r3,0x4(r30) / stw r0,0x8(r30)` is the member-initialiser list over **other**; the two
  `cmpwi`s are `other.mCount == 0 && other.mCapacity == 0`; `slwi r3,r0,3` is
  `mCapacity * sizeof(rstl::pair<uint,uint>)`; and after the `bl`, `lwz r5,0xc(r31)` takes the
  **source** from *other* while `lwz r3,0x4(r30) / lwz r4,0xc(r30)` take the count and the
  **destination** from *self* - which is why the loop is driven by `self->mCount` and not
  `other->mCount`. The other four copies of these bytes across `main` are the named COMDAT at
  0x80004F5C, `fn_80005158`, `fn_801EF8B8` and `fn_8018FE6C`.
- **`fn_800039C4`** vs `fn_80004744` (0x80004744, 0x54, `src/MetroidPrime/Carve80004744.c`). Two
  168-hex-digit streams; they differ only at instructions 9 and 13 - the two `bl` into
  `Free__7CMemoryFPCv`. Those two are relocations, and `powerpc-eabi-objdump -r` on the finished
  object confirms exactly three of them and the right targets:
  `0x50 R_PPC_REL24 allocate__Q24rstl17rmemory_allocatorFi`,
  `0x16c / 0x17c R_PPC_REL24 Free__7CMemoryFPCv`.
  `Carve80004744.c`'s own header documents the deleting-destructor family, its three call sites and
  why the member is a plain pointer (no count load, no stride, no element loop).
